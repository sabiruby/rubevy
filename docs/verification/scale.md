# 規模 — この機械で何が載るか（R1〜R5 の前後と、今の数字）

2026-09-20。`docs/plans/generalize-plan.md` の R1〜R4 が直した 4 つと、R5 が足した見え方を、
**同じ日・同じ機械・同じ条件**で 1 枚にしたもの。前の数字は各段階の worklog から取り、
後ろの数字は R5 の終わりの状態で常設の計測器 2 本を回し直したものである。

計測器はこの repo の example で、**assert しない計測器**（`tests/read_cost.rs` と同じ流儀）:

```bash
cargo run --release --example how_many_scripts        # スクリプト付きエンティティ
cargo run --release --example how_many_subscribers    # 購読者とイベント
```

## 条件

- 13th Gen Intel Core i7-13700、WSL2（Linux 6.18.33.2-microsoft-standard-WSL2）、`--release`、`taskset -c 2`（P コア固定）
- **sabiruby 0.5.2（crates.io）/ bevy 0.19.1**、rustc 1.97.0。`.cargo/config.toml` は無く、隣の checkout は使っていない
- ヘッドレス（`MinimalPlugins` + `AssetPlugin` + `RubevyPlugin`）、ネイティブ専用
- 計測の前後に `pgrep -af "cargo|rustc|docker run|chrome|wasm-opt|wasm-bindgen"` が空であることを確かめた

読み取れること:

1. **`frame_time` は守られている。** 1000 台と 3000 台の `default` の `FrameStats` の tick は
   **8.05〜8.06 ms**（設定 8 ms）、`tight` は **1.02〜1.04 ms**（設定 1 ms）。R4 の前は同じ行が
   14.91 ms と 3.27 ms だった。超過はどの行も 0.06 ms 以下で、これは「必ず 1 件は答える」の 1 件ぶんである
   （`いちばん長い答え` の列がその 1 件の大きさで、3000 台の `tight` で 50.9 µs）。
2. **代償は `持ち越し` の列に出る。** 3000 台 `tight` は 1 フレームに 76 件しか答えず、2876 件を次のフレームへ送る。
   1 台が動ける間隔は 45〜90 フレーム。どの行も min ≒ med ≒ max で**飢えているタスクは無い**
   （R4 の結論と同じ）。
3. **毎フレーム全台が動ける形は約 300〜1000 台**（`generous` の行が「限界を外したときの実費」）。
   300 台で 3.8 ms、1000 台で 16.8 ms、3000 台で 83 ms。60 Hz に載るのは 1000 台のあたりまで。

### いちばん長かった答え 1 件（`FrameStats::longest_answer_ns`）

この列は**上の表から外してある**。最初の実装は区間の頭を「その周回の答えが始まる前」ではなく
「周回の頭」に置いていたので、1 件目の答えに**その周回の VM の実行と、問いを VM のキューから
取り出す仕事**が乗っていた。直した（`clock.start()` を 2 つの答え関数の中に移した）あと、
同じ機械で**直す前と直した後のバイナリを交互に 2 巡**走らせた（1000 台、60 フレーム、1 回ずつ）:

| limits | 直す前 | 直した後 | 同じ run の tick（`FrameStats`） |
|---|---|---|---|
| default(200k/8ms) | 325.6 / 560.4 µs | **23.2 / 25.6 µs** | 8.10 / 8.04 ms 対 8.03 / 8.03 ms |
| tight(200k/1ms) | 38.1 / 44.5 µs | **22.6 / 21.8 µs** | 1.03 / 1.03 ms 対 1.02 / 1.02 ms |
| clocked(100M/1s) | 693.8 / 753.4 µs | **69.5 / 31.4 µs** | 16.7 / 17.5 ms 対 17.1 / 17.2 ms |
| default+bare | 565.1 / 536.9 µs | **24.5 / 20.2 µs** | 8.01 / 8.01 ms 対 8.02 / 8.01 ms |

直した後の **20〜70 µs** が、この計測器の in-tick の閉包（`world.get::<Dial>()` 1 回）と
component の読み 1 件（`tests/read_cost.rs` で 2.2〜2.4 µs）を含む「いちばん高かった 1 件」である。
tick の実時間は**同じ**なので、周回ごとに増えた時計 1 回は測れる費用ではない。
**この 2 巡は隣の担当のビルドが走っている間に取った**（だから絶対値は上の表より大きい）。
前後を交互に取ってあるので、比べている列については読める。
上の表の残りの列は、この直しの影響を受けない（直したのは測り方であって、答える仕事ではない）。

**注意（罠 4、下の 7 節）**: `generous` と `clocked` の行は、**同じバイナリ・同じ設定でも
走らせ方によって 2.5 倍動く**。上の 1000 台 `generous` は 18.3 ms だが、その行だけを別プロセスで
走らせると 6.6〜6.9 ms になる（原型の計測器も同じ 2 つの値を出す）。フレームが 16.7 ms を超えると
ペース用の `sleep` が消えて CPU が 100% になり、超えないと半分眠る — という**自己維持する 2 状態**に
見えるが、**WSL2 は CPU の周波数を見せないので確かめていない**。
`default` と `tight`（フレームが 16.7 ms に収まる行）は走らせ方によらず安定している。

## 3. 外から測った tick と、rubevy が言う tick

R1〜R4 の計測器は tick の実時間を「`RubevySet::Tick` の前後に置いた 2 つのシステム」で測っていた。
`RubevySet::Tick` には**システムが 4 つ**入っている（`tick_scripts`、`drain_commands`、
`apply_component_writes`、`apply_resource_writes`。`src/lib.rs` の `RubevySet` の表）ので、
外から挟むと 4 つ全部を測る。`FrameStats::time_ns` は `tick_scripts` だけである。
上の表の 2 つの列の差:

| 台数（default） | 外から | `FrameStats` | 差 |
|---|---|---|---|
| 10 | 134.5 µs | 85.7 µs | +48.8 µs |
| 100 | 1.264 ms | 1.153 ms | +0.111 ms |
| 300 | 4.338 ms | 4.072 ms | +0.266 ms |
| 1000 | 8.838 ms | 8.060 ms | +0.778 ms |
| 3000 | 8.537 ms | 8.052 ms | +0.485 ms |

差は台数とともに増える（コマンドの実行とフレーム末尾の書きが台数ぶんあるため）。
**`frame_time` が縛るのは小さいほう**なので、「`frame_time` を 8 ms にしたのに tick が 8.8 ms ある」と
見えたときは、まずどちらを測っているかを確かめる。R4 の worklog の表は外から測った数だが、
前後で同じ計器を使っているので**差は差**である（絶対値がコマンドと書きを含む、というだけ）。

読み取れること:

1. **誰も聞いていない名前への publish は購読の総数に依らない**（R1）。1 件あたり
   11.9 / 9.0 / 14.0 / 12.4 ns（S = 1 / 10 / 100 / 1000、P = 1000 の列）。前は 7.9 → 228 ns と
   購読数に比例して上がっていた。
2. **1 本の購読者が 60 フレームで読めるのは 3840 件**（= 64 × 60、既定の上限が決めている）。
   上限を上げたときにどこで止まるかは 5 節。
3. **`1000 × 1000` は成立しない**（フレーム 109 ms、うち 106 ms が publish）。これは R1 の前後で変わらない
   — 聞く人がいる publish は購読者ごとに値を作るからである（計画書 5 章、`publish_shared` は今回やらない）。
4. **tick の時間は購読者の数で決まり、件数ではあまり動かない**（`1000 × 10` と `1000 × 1000` で
   2.76 ms と 2.96 ms）。読み手が起きて `pop` する費用と、VM が待ちタスクを走査する費用である。
5. `1 × 1000` のセルは走るたびに大きく動く（R1・R3 とも判断を保留した）。上の 330 µs も 1 回の測定でしかない。

## 5. 1 本の購読者が 1 フレームに読み切れる件数（上限を動かす）

`how_many_subscribers limit 60 3`。購読者 1 本、ホストは毎フレーム 8192 件 publish、
予算は既定のまま（200,000 命令 / `frame_time` 8 ms）、上限だけを動かす。R3 が 1 回ずつ取った表を、
**繰り返し 3 回の中央値**で取り直したもの（R3 の「上限 4096 の行だけ跳ねた」は繰り返しが 1 回だったため）。

| 上限 | 1 フレームに読めた件数 | 落とした（60 フレーム） |
|---|---|---|
| 1 | 1.0 | 491460 |
| 16 | 16.0 | 490560 |
| **64（既定）** | **64.0** | 487680 |
| 128 | 128.0 | 483840 |
| 256 | 256.0 | 476160 |
| 512 | 512.0 | 460800 |
| 1024 | 1024.0 | 430080 |
| 2048 | 2048.0 | 368640 |
| 4096 | **3822.2** | 262191 |
| 8192 | **3828.2** | 261826 |

**天井は約 3,800 件/フレーム**で、R3 の 3,877 / 3,960 と同じ範囲にある。止めているのは命令の予算
（200,000 ÷ 3,800 ≒ 53 命令/件）。既定の 64 はその約 1/60 で、**「64 件が天井」だった調査の数字は

なお **この表のフレーム時間の列は隣の担当のビルドが走っている間に取ったので載せていない**
（件数と落とした数は CPU の混み具合では動かない）。

## 6. メモリ

**1 台あたり**（`how_many_scripts mem <台数> 60`、台数ごとに別プロセス。`started` は起動直後、
`running` は 60 フレーム走らせた後、どちらも VM だけのプロセスとの差を台数で割った値）:

| 台数 | 起動直後 kB/台 | 走らせた後 kB/台 | プロセスの RSS（走行後） |
|---|---|---|---|
| 10 | 2.80 | 130.40 | 22.9 MB |
| 100 | 1.68 | 20.24 | 23.2 MB |
| 300 | 1.65 | 10.37 | 24.3 MB |
| 1000 | 1.46 | 8.06 | 29.5 MB |
| 3000 | 1.46 | 8.33 | 46.6 MB |

R2 の後の数字（1.46 kB / 8.11〜8.38 kB）と同じである。**3000 台で 46.6 MB** — 制約にならない。
小さい台数の「走らせた後」が大きいのは、VM のヒープが台数に依らず育つぶんを少ない台数で割っているから。

**溜まったメッセージ 1 件あたり**（`how_many_subscribers mem <上限> <購読者>`。読まない購読者のキューを
上限まで埋め、前後の RSS の差を件数で割る）:

| payload | 上限 1000 × 10 本 | 上限 10000 × 10 本 | 上限 64 × 1000 本 |
|---|---|---|---|
| `Num` | 20.9 B | 20.8 B | 15.6 B |
| `Text`（8 バイト） | 309.7 B | 316.0 B | 334.1 B |
| `List`（Float 4 個） | 530.4 B | 362.7 B | 331.5 B |

R3 の表（20.9 / 307.2 / 521.4 …）とほぼ同じ。**短い文字列 1 件が 300 B 超**なのは VM のヒープ
オブジェクト 1 個の値段で、`Answer::Text` を大量に publish するゲームは数値の 15〜20 倍を使う。
`List` の行が上限 1000 と 10000 で 530 B と 363 B に割れるのは R3 でも同じで、**理由は分かっていない**。

## 7. 再現の手順（と、前の担当が踏んだ罠）

```bash
cd rubevy-wt-generalize
CARGO_TARGET_DIR=../rubevy/target cargo build --release --example how_many_scripts --example how_many_subscribers
taskset -c 2 <bin>/how_many_scripts 90 3            # 表ぜんぶ（約 10 分）
taskset -c 2 <bin>/how_many_scripts 90 3 1000 0.004 # 1 行だけ
for n in 10 100 300 1000 3000; do taskset -c 2 <bin>/how_many_scripts mem $n 60; done
taskset -c 2 <bin>/how_many_subscribers 60 3        # 購読者 × 件数（約 6 分）
taskset -c 2 <bin>/how_many_subscribers limit 60 3
taskset -c 2 <bin>/how_many_subscribers mem 1000 10
```

前後を比べるときは、前の版を別の worktree に建てる:

```bash
git -C rubevy worktree add --detach ../rubevy-wt-<段階>-before <前のコミット>
cd rubevy-wt-<段階>-before
CARGO_TARGET_DIR=<別の場所> cargo build --release --example <計測器>
md5sum <前のバイナリ> <後のバイナリ>      # 別物であることを必ず確かめる
```

**罠 1: 同じ `CARGO_TARGET_DIR` で 2 つの worktree の example を建てると、2 つ目が建たない。**
cargo は「変更なし」と見て 0.1 秒で終わり、`target/release/examples/<名前>` は 1 つ目のバイナリのまま残る
（uplift されるファイル名が同じで、cargo が別パッケージと見ていないため）。**`md5sum` が一致したら測る前に気づく。**
R1 の担当はこれを踏みかけた。

**罠 2: 共有の target は古い成果物を返すことがある。** `src/lib.rs` を書き換えて `cargo build --lib` が通った直後の
`cargo test` が、無いはずのものが無いと言って落ちた（R3）。`touch src/lib.rs` してから建て直す。

**罠 3: 隣で cargo・docker・ブラウザが動いていると p95 が跳ねる。** R1 の測定中に隣の担当の
`docker run … cargo build` が走り、`100 × 1000` のセルの p95 が 28.5 ms 対 12.2 ms になった。
走らせる前と後に `pgrep -af "cargo|rustc|docker run|chrome|wasm-opt|wasm-bindgen"` を見る。

**罠 4: 機械には「遅い状態」がある。** R5 の担当は、同じバイナリ・同じ設定の 1000 台 `generous` の行が
6.8 ms と 18.7 ms に割れるのを見た（どちらも `pgrep` は空）。直前まで別の測定やビルドが走っていた後の
1 回目が遅い。**計測器を 2 本並べて比べるときは、必ず交互に 2 巡**（前 → 後 → 前 → 後）走らせる。
1 巡目だけを見ると、「遅い状態」のほうを「遅い版」と読み違える。

**`1 購読 × 1000 件` のセルは走るたびに ±40% 動く**（R1・R3 とも判断を保留した）。
このセルだけは 1 回の測定から何も言えない。

## 8. 測っていないこと

入れ子の payload（Hash / Array）の publish、エンティティ宛の publish、1 台が購読を複数本持つ形、
優先度を分けたときの飢え、走行中の大量の建設・撤去、wasm、
そして `Vm::task_pending()` が待ちタスクを最後まで歩く形（全タスクが期限の無い `q.pop` で止まっているゲーム）。
