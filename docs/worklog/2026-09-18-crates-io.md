# git 依存を版に替えて crates.io に出せる形にする（P1）

2026-09-18。計画書 `docs/plans/publish-plan.md` の段階 P1。ブランチ `publish`、worktree
`../rubevy-wt-publish`。公開そのもの（`cargo publish`）と main への merge・push は本体の仕事なので、
ここでやったのは `--dry-run` まで。

## 前提を確かめる

計画書は「crates.io は git 依存のある crate を受け付けない」から始まっている。手を付ける前に
`Cargo.toml` の実物を読んだ。git 依存は 5 か所あった — `[dependencies]` の `sabiruby` と
optional の `sabiruby-compiler`、`[dev-dependencies]` の `sabiruby-compiler`・`sabiruby`
（feature `macros`）・`sabiruby-serde`。`Cargo.lock` の 2846 行目以降を見ると、4 つとも
`git+https://github.com/sabiruby/sabiruby#e2470626…`、つまり 0.5.0 の頃の rev で止まっていた。
計画書の「今」の欄はそのとおりだった。

## 下限の版を、書いた数の出どころごと manifest に残す

計画書 §2.1 が下限を `sabiruby = "0.5.1"`、`sabiruby-compiler = "0.2.2"`、
`sabiruby-serde = "0.1.0"` と決めている。数そのものより、その数がどこから来たかを manifest の
コメントに 1 行で書けることのほうが後で効くので、`sabiruby` のコメントには
「0.5.1 はスケジューラの修正（nil で終わるタスク、dormant キュー）を持つ最初の版で、0.5.0 では
10 本同時差し替えで VM が止まる」と、その結論を出した worklog
（`2026-09-17-restart-burst.md`）へのポインタを書いた。`sabiruby-compiler` のほうは
「0.5.x の VM を名指しする最初の compiler、rubevy は `highlight()` を呼ばない」。

`rust-version` は「測って決める」ことになっていたので、`cargo metadata --format-version 1
--filter-platform x86_64-unknown-linux-gnu` の出力から依存の `rust_version` を全部取り出した:

```
bevy 0.19.1        rust-version = 1.95.0
sabiruby 0.5.x     rust-version = 1.85
sabiruby-compiler  rust-version = 1.85
thiserror 2.0.20   rust-version = 1.71
```

いちばん大きいのは bevy の 1.95.0 なので、`rust-version = "1.95.0"` と書き、その出どころ
（誰が何と言っているか）をコメントに残した。手元の rustc は 1.97.0 なので、この宣言でビルドは通る。

`categories` は crates.io の `/api/v1/categories?per_page=100`（User-Agent はリポジトリ名。
個人のメールアドレスは入れない）で一覧を取って、slug と説明を突き合わせた。`game-development` の
説明は "For crates that focus on some individual part of accelerating the development of games."
で、rubevy はまさにその一部分（スクリプト）なので、これ 1 つにした。`game-engines` は
"one-stop-shop for all of your game development needs" で rubevy ではない。`api-bindings` は
"Idiomatic wrappers of specific APIs" で、これも違う（rubevy は VM をゲームループに載せる側であって、
既存 API の薄い包みではない）。当てはまらない slug を検索性のために足すのはやめた。

`repository` と `readme` は計画書のとおり。

## 隣の checkout に向ける道を閉じない

git 依存をやめると `[patch."https://github.com/sabiruby/sabiruby"]` が効かなくなる。`Cargo.toml`
のコメントと README の「Try it」に書いてあった手順がそのままでは嘘になるので、両方を
`[patch.crates-io]` の形に書き換えた。crates.io の版を名指ししているのだから patch も
crates-io の側に掛ける、というだけの話だが、書いてある手順が動かない文書は無いほうがましなので
直した。

## 確認

`cargo update` で lock を crates.io の最新（`sabiruby` 0.5.2、`sabiruby-compiler` 0.2.3、
`sabiruby-macros` 0.1.0、`sabiruby-serde` 0.1.0）に移した。lock の source 行が 4 つとも
`registry+https://github.com/rust-lang/crates.io-index` に変わったことを目で見た。

* `cargo test`（feature なし）: **75 passed, 0 failed, 2 ignored**。ignored の 2 つは
  `tests/read_cost.rs` の計測用（もともと `#[ignore]`）。
* `cargo test --features ruby-source`: 同じく **75 passed, 0 failed, 2 ignored**。
  ただし最初の 1 回だけ `tests/child_task.rs` が 3 本中 1 本落ちた。同じコマンドをもう一度
  回すと通り、`--test child_task` だけを 3 回続けて回しても 3 回とも 3/3 通った
  （合計 4 回の再現試行で 0 回再現）。最初の 1 回は C の compiler をビルドしながら走っていて
  機械が混んでいた。`docs/worklog/2026-09-18-wasm-instant.md` にも「機械が混んでいて落ちた
  `tests/pause.rs` が変更とは無関係だった」という同じ形の記録がある。依存の版を替えた変更で
  child_task が壊れるなら再現するはずなので、負荷による揺れと判断した。**再現しなかったという
  以上のことは確かめていない**ので、ここに残す。
* 下限の版で: `cargo update -p sabiruby --precise 0.5.1` と
  `cargo update -p sabiruby-compiler --precise 0.2.2` を掛けてから `cargo test` と
  `cargo test --features ruby-source`。どちらも **75 passed, 0 failed, 2 ignored**。
  計画書が「通らなければ勝手に上げずに止まって報告」と言っていた場所だが、通ったので下限は
  そのまま。終わってから `cargo update` で最新に戻し、その lock をコミットした。
* `cargo tree -d`: 重複の根は `foldhash`、`hashbrown`、`linux-raw-sys`、`rustix`、`syn`、
  `thiserror` の 6 種で、**`sabiruby` は無い**。`cargo tree -i sabiruby` は
  `sabiruby v0.5.2` 1 つだけを根に、rubevy 本体・`sabiruby-compiler`・`sabiruby-serde` の
  3 経路がそこに集まる形を出した。`cargo tree -d | grep sabiruby` は空にならないが、それは
  `foldhash`/`hashbrown` の重複の木の中に「hashbrown を使っている者」として sabiruby の名前が
  出てくるからで、重複しているのは hashbrown のほう（sabiruby 経由の 0.15.5 と bevy 経由の
  0.16/0.17）。この重複は版に替える前からあり、今回の変更とは関係が無い。
* `tests/no_wasm_unsupported.rs`（`bcb9cc0` で入れた wasm の番人）: 2 passed。
* `cargo check --target wasm32-unknown-unknown`（feature なし）: 通る。
* `cargo doc --no-deps`: **警告 3 → 0**。下に書く。
* `cargo publish --dry-run`: verify まで通り、`Packaged 87 files, 933.5KiB
  (296.2KiB compressed)`。

## rustdoc の警告 3 つを消した（src/ に入れた唯一の変更）

`cargo doc --no-deps` は最初 3 つ警告を出した。3 つとも同じ形で、
`public documentation for X links to private item Y`:

```
src/lib.rs:866   take_requests   -> [`RESERVED_KINDS`]   (private const)
src/lib.rs:926   answer_in_tick  -> [`RESERVED_KINDS`]
src/lib.rs:1360  RubevySet       -> [`tick_scripts`]     (private fn)
```

これは今回の変更が作った警告ではなく前からあったもので、放っておいても公開はできる。ただ
docs.rs に出るページの見た目の話なので、計画書は P1 の確認に「警告 0」を入れている。直し方は
リンクをやめて素のコード span にするだけにした（`[`RESERVED_KINDS`]` → `` `RESERVED_KINDS` ``）。
`--document-private-items` を渡す道もあるが、それは docs.rs の設定を増やすうえに、非公開の
関数を公開のページに出すことになる。素の span にする形は同じファイルの 1323 行目
（`` `tick_scripts` ``）に既にあった書き方で、それに合わせた。

私有の項目を指している同じ書き方はほかにもある（726・731 行目の `RESERVED_KINDS` と
`tick_scripts`、1603・1784・1940・2065 行目の `tick_scripts`）。これらは警告に出ない —
書かれている側の項目自体が非公開（`reflect_requests` フィールドや private fn の rustdoc）で、
rustdoc は公開のページに出るものしか見ないからだ。出ない以上そのままにした。**動く字は
1 文字も変えていない**（3 か所とも rustdoc コメントの中の角括弧だけ）。

## 中身は削らなかった

計画書 3 は「crate に要らない大きなものが入っていないか見る」と言っている。`cargo package
--list` は（この記録自身を入れて）87 ファイル、内訳は docs 27、assets 24、tests 17、examples 7、
src 4、tools 1、あとは README・LICENSE・lock など。展開して 933.5 KiB、圧縮して 296.2 KiB。crates.io の上限は
10 MiB なので、その 3% 弱にしかならない。

* `assets/` の 24 個は `.rb` と `.mrb` が対。examples はこれを読んで動く（`headless`、
  `sensor`、`components`、`nearest`、`events`、`two_vms`）ので、計画書の条件どおり残す。
  全部で 28 KiB しかない。
* `docs/` は 512 KiB とこの crate でいちばん大きいが、sabiruby 自身の manifest も
  `include` に `/docs/**/*.md` を入れていて、組織の既定はドキュメントを一緒に配ること。
  README が `docs/host-api.md` と `docs/rust-bridge.ja.md` を指してもいる。
* `tests/` 132 KiB は、この crate を取った人が `cargo test` を回せる値打ちのほうが大きい。

つまり **`exclude` は足さなかった**。足す理由（上限に近い、無関係な巨大ファイル）がどれも
無く、根拠の無い線引きになるため。前後のサイズを比べるまでもない、というのが判断。
上限に近づいたら、そのときの数を見て決める。
