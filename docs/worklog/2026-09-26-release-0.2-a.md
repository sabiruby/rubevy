## 1. R3: `Entity::try_from_bits(u64::MAX)` が `Some` を返す

### 1.1 何が起きていたか

`install_host_api`（`src/lib.rs`）の `Rubevy.ask`・`set_component`・`set_resource` の 3 つの
ネイティブは、走っているタスクのエンティティを

```rust
let entity = match current_entity(vm) { Value::Int(bits) => bits as u64, _ => u64::MAX };
```

と読んでいた。`u64::MAX` が「このタスクにはエンティティが無い」の綴りで、`drain_commands` と
`take_asks` がそれを `entity_from_bits`（= `Entity::try_from_bits`）に通す。held-requests の
worklog の気づいた点 3 が言うとおり、これが `Some` を返す。

なぜ `Some` なのかを bevy_ecs 0.19.1 で読んだ。`Entity::try_from_bits`（`src/entity/mod.rs:592`）は
下位 32 ビットを `EntityIndex::try_from_bits` に、上位 32 ビットをそのまま世代にする。
`EntityIndex` は `NonMaxU32` で、`to_bits` / `try_from_bits`（同 180・203 行）はその中身を
`transmute` で出し入れするだけ。`NonMaxU32` は「値の補数を `NonZero` に入れる」形なので、**拒まれる
下位ビットは 0 だけ**で、`u32::MAX` は「添字 0」として通る。つまり `u64::MAX` は
**添字 0・世代 `u32::MAX` のエンティティ**である。テストの失敗の表示が `Some(0v4294967295)` —
添字 0、世代 4294967295 — だったのがそれを裏付けている。

影響は 2 つあった。

* `Request::entity` が、rustdoc の「where it has one」に反して `None` にならない。held-requests の
  worklog のとおり、sabibots はたまたま `commands.get_entity(e).is_err()` で弾き、garden は索引に
  使うだけなので当たっていなかった。
* もう 1 つは書いた本人も気づいていなかったもの: `set_component` / `set_resource` の `by` も同じ
  綴りなので、エンティティの無いタスクが拒まれた書き込みの `RejectedWrite::by` も `Some(存在しない
  エンティティ)` になっていた。

### 1.2 直し方の選択

案は 3 つあった。

1. `entity_from_bits` で `u64::MAX` だけ `None` にする。— 番兵を残すことになり、しかも **添字 0・
   世代 `u32::MAX` という本物のエンティティ**（添字 0 を 40 億回使い回した後）を 1 つ潰す。
2. 番兵を `0` に変える。`try_from_bits(0)` は `None` なので動くが、それは Bevy の中の表現
   （`NonMaxU32` の補数）を当てにしている。rustdoc は bits を「opaque」と言っている。
3. **番兵をやめて `Option<u64>` にする。** `HostCommand` は非公開の型なので、公開の API は変わらない。

3 にした。「エンティティが無い」を数で綴るのをやめれば、どの数が Bevy にとって何なのかを考える
必要自体が無くなる。ネイティブ側は `task_entity(vm) -> Option<u64>` を 1 つ足して 3 か所で使い、
受け側は `entity.and_then(entity_from_bits)` にした。`current_entity` はそのまま（`Rubevy.entity`
と `Rubevy.move_to` と `subscribe` は元から `Value::Int` かどうかで分けていて、番兵を使っていない）。
