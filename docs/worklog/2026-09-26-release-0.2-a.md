## 1. R3: `Entity::try_from_bits(u64::MAX)` が `Some` を返す

### 1.1 何が起きていたか

`install_host_api`（`src/lib.rs`）の `Rubevy.ask`・`set_component`・`set_resource` の 3 つの
ネイティブは、走っているタスクのエンティティを

```rust
let entity = match current_entity(vm) { Value::Int(bits) => bits as u64, _ => u64::MAX };
```

と読んでいた。`u64::MAX` が「このタスクにはエンティティが無い」の綴りで、`drain_commands` と
`take_asks` がそれを `entity_from_bits`（= `Entity::try_from_bits`）に通す。held-requests の
worklog の気づいた点 3 が言うとおり、これが `Some` を返す。

なぜ `Some` なのかを bevy_ecs 0.19.1 で読んだ。`Entity::try_from_bits`（`src/entity/mod.rs:592`）は
下位 32 ビットを `EntityIndex::try_from_bits` に、上位 32 ビットをそのまま世代にする。
`EntityIndex` は `NonMaxU32` で、`to_bits` / `try_from_bits`（同 180・203 行）はその中身を
`transmute` で出し入れするだけ。`NonMaxU32` は「値の補数を `NonZero` に入れる」形なので、**拒まれる
下位ビットは 0 だけ**で、`u32::MAX` は「添字 0」として通る。つまり `u64::MAX` は
**添字 0・世代 `u32::MAX` のエンティティ**である。テストの失敗の表示が `Some(0v4294967295)` —
添字 0、世代 4294967295 — だったのがそれを裏付けている。

影響は 2 つあった。

* `Request::entity` が、rustdoc の「where it has one」に反して `None` にならない。held-requests の
  worklog のとおり、sabibots はたまたま `commands.get_entity(e).is_err()` で弾き、garden は索引に
  使うだけなので当たっていなかった。
* もう 1 つは書いた本人も気づいていなかったもの: `set_component` / `set_resource` の `by` も同じ
  綴りなので、エンティティの無いタスクが拒まれた書き込みの `RejectedWrite::by` も `Some(存在しない
  エンティティ)` になっていた。

### 1.2 直し方の選択

案は 3 つあった。

1. `entity_from_bits` で `u64::MAX` だけ `None` にする。— 番兵を残すことになり、しかも **添字 0・
   世代 `u32::MAX` という本物のエンティティ**（添字 0 を 40 億回使い回した後）を 1 つ潰す。
2. 番兵を `0` に変える。`try_from_bits(0)` は `None` なので動くが、それは Bevy の中の表現
   （`NonMaxU32` の補数）を当てにしている。rustdoc は bits を「opaque」と言っている。
3. **番兵をやめて `Option<u64>` にする。** `HostCommand` は非公開の型なので、公開の API は変わらない。

3 にした。「エンティティが無い」を数で綴るのをやめれば、どの数が Bevy にとって何なのかを考える
必要自体が無くなる。ネイティブ側は `task_entity(vm) -> Option<u64>` を 1 つ足して 3 か所で使い、
受け側は `entity.and_then(entity_from_bits)` にした。`current_entity` はそのまま（`Rubevy.entity`
と `Rubevy.move_to` と `subscribe` は元から `Value::Int` かどうかで分けていて、番兵を使っていない）。

### 1.3 確かめたこと

`tests/no_entity.rs` を足した（4 本）:

* `u64_max_is_an_entity_to_bevy` — 直す理由そのもの。`Entity::try_from_bits(u64::MAX)` が `Some` で、
  `to_bits` で同じ数に戻る。
* `a_question_from_a_task_with_no_entity_has_no_entity` — ホストが `task_spawn` で起こしたタスク
  （`Script` の外）が `Rubevy.ask` すると `entity == None`。
* `a_task_that_cleared_its_entity_asks_as_nobody` — スクリプトが自分の `@rubevy_entity` を nil に
  してから問う、もう 1 つの道。
* `a_refused_write_by_a_task_with_no_entity_is_by_nobody` — 拒まれた `set_resource` の `by` が `None`。

**直す前のコードで落ちることを確かめた**（`git diff src/lib.rs` をスクラッチに書き出して
`git checkout src/lib.rs`、テストを走らせて `git apply` で戻した。stash は使っていない）。
1 本目は通り、残り 3 本が `left: Some(0v4294967295) right: None` で落ちた。直した後は 4 本とも通る。

## 2. R4: `ScriptStats::location` / `frames` が前置きの行数を引いていない

### 2.1 どこで何が足りなかったか

`ScriptWorld::stats(&ScriptTask)` は `vm.task_location(task)` と `vm.task_frames(task)` をそのまま
返していた。`prelude_lines` は H2 で `Script` に入ったが（`ScriptEnded::at` のため）、`stats` が
渡されるのは `ScriptTask` で、`Script` ではない。だからゲームが自分で引いていた:
rubevy_games の Battle（`sabibots/src/main.rs:3457` 付近の HUD）は `location` と `frames` の両方から
`robot.prelude_lines` を引き、`rubevy-egui` の `VmInspector::fill` は `stats` を使わずに
`vm.task_frames` を読んで同じ引き算をしている。

**`ScriptTask` に `prelude_lines` を写す**ことにした。`start_scripts` が `Script` から `ScriptTask` を
作るところで写すだけで、`ScriptTask` の欄は非公開なので API の形は変わらない（`Copy` のまま、
`u32` が 1 つ増えるだけ）。`stats(&ScriptTask, prelude_lines)` のように引数を足す案は、呼ぶ側が
また数を持ち回ることになるので採らなかった。タスクは始まったときのプログラムを走らせ続けるので、
始まったときの `Script` の数を写すのが正しい（後から `Script` の数を書き換えても、走っている
プログラムの前置きは変わらない）。

### 2.2 前置きの中のフレームをどう答えるか

引くのは簡単だが、**前置きの中に立っているフレーム**（行が `1..=prelude_lines`）をどうするかは
決めることがあった。前置きは作者のファイルと同じファイル名でコンパイルされる（`Program::new` が
1 つのソースにつなぐ）ので、(`"player.rb"`, 2) と返すと、作者のファイルの 2 行目なのか前置きの
2 行目なのか区別できない。案は 3 つ:

1. そのまま（引かずに）残す — 区別できない数を作者のファイル名で出すことになる。
2. 前置きのファイル名を付けて出す — rubevy は前置きの名前を知らない（`in_the_authors_lines` は
   引数で受け取るが、`Script` には無い）。`ScriptStats` の形も変わる。
3. **外す** — `ScriptEnded::at` がしていること（前置きのフレームは飛ばして、外側の作者の行を答える）。

3 にした。原則は「クレートの中で同じ問いには同じ線を引く」で、`ScriptEnded::at` の rustdoc が
すでに「`at` が `(file, line)` なのは `ScriptStats::location` / `frames` と同じ形だから」と言って
いる。形が同じなら数え方も同じであるべきだ。線を引く関数を `authors_place(line, prelude_lines)`
として 1 つにし、`authors_line`（`at` の方）と `stats` の両方から呼ぶ。行 0（VM が場所を付けられ
なかったフレーム。backtrace なら `:0`）も同じく外れる。

前置き無し（`prelude_lines == 0`）では、外れるのは行 0 のフレームだけになる。`task_location` は
`task_frames` の先頭と同じもの（SabiRuby 0.6.1 `ext_task.rs:226` と `:245` が同じ走査で、前者は
最初の 1 つで止まる）なので、`location` は外した後の `frames` の先頭にした。これで VM への問い合わせ
も 2 回から 1 回になる。前置きを含めた VM の生の見え方が欲しい panel のために、rustdoc に
`vm.task_frames(task.task())` を読めばよいと書いた（rubevy-egui はすでにそうしている）。

### 2.3 確かめたこと

`tests/script_ended_at.rs` に 3 本足した:

* `stats_answers_in_the_authors_lines` — 前置きの `def scan … Rubevy.ask('scan').pop` の中で待って
  いるスクリプト。`location` は作者の 2 行目（`scan` を呼んだ行）、`frames` はその 1 つだけ。
* `stats_takes_the_prelude_off_a_line_of_the_authors_own` — 作者の 3 行目で待っている。
* `stats_without_a_prelude_is_the_vms_own` — 前置き無しなら `task_frames` / `task_location` と同じ。

直す前のコードでは前 2 本が落ちた:

```
assertion `left == right` failed: and not the prelude's line 2
  left: [("player.rb", 2), ("player.rb", 7)]
 right: [("player.rb", 2)]
assertion `left == right` failed
  left: Some(("player.rb", 7))
 right: Some(("player.rb", 3))
```

1 本目は `location` の方がたまたま一致していた（前置きの `Rubevy.ask` が前置きの 2 行目、作者の
`scan` が作者の 2 行目）。`frames` を見ていなければ見逃していたので、両方を確かめる形にしてある。

### 2.4 使う側への影響

**Battle（sabibots）の HUD は二重に引くことになる。** `sabibots/src/main.rs:3457` 付近が
`stats.location` と `stats.frames` から自分で `robot.prelude_lines` を引いているので、0.2.0 に上げる
ときにその引き算を消す必要がある（前置きの中にいるときの `"prelude.rb:{line}"` の表示は、
`location` が `None` になった場合に出すか、`vm.task_frames` を読む形に変わる）。games 側の直しは
段階 D。`rubevy-egui` と garden は `stats` の `instructions` しか読まないか、`task_frames` を直接
読んでいるので影響は無い。

## 3. R2: 答えずに捨てた `Request` — 登録の漏れと、閉じないキュー

### 3.1 何が起きていたか

`Rubevy.ask` のネイティブ（`install_host_api`）はキューを作って `gc_register` する。それを外すのは
`ScriptWorld::push_answer`（`answer` / `answer_value` / `answer_with` の行き着く先）だけだった。
`Held` の removal hook（`release_held`）が H1 で 2 か所目になったが、それは `Held` に入っている
問いだけで、`take_requests` で取り出した `Request` をゲームが落とせば、キューは VM の寿命ぶん
登録されたまま、そこで待っているタスクも VM の寿命ぶん待つ。held-requests の worklog の
気づいた点 2 と 4 で、4 の「閉じるかどうか」は著者の判断待ちになっていた。
**著者の判断（2026-09-26）: 閉じる。待っている側は例外で知る。**

### 3.2 捨てたことをどう知るか — 明示の口か、`Drop` か

計画書は「`ScriptWorld::forget(&Request)` が無い」と書いているが、それを足す案は採らなかった。
`forget` を呼び忘れたら今と同じことが起きる。**すでに同じ形の問題を同じクレートが解いている**:
`Arg::Value` が運ぶ Hash は `RootedValue` が持ち、最後のクローンの `Drop` が release queue に積み、
次のフレームの頭の掃除（`release_dropped_values`）が `gc_unregister` する。`host-api.md` も
「There is no `release(request)` to forget」と書いている。問いのキューも同じ道に乗せるのが、
既存の流儀に合わせるということだと判断した。

形はこうした:

* `QuestionRoot { queue, answered: AtomicBool, release }` を `Arc` で `Request` の非公開の欄に持つ
  （`Request` は `Clone` のまま。クローンは同じ `Arc` を持つ）。ネイティブが `gc_register` した
  直後に作るので、`HostCommand::Ask` の段階から持ち主がいる。
* `answer` は `answered` を `swap(true)` してから push と `gc_unregister` をする。
* `Drop` は `answered` が立っていなければ `Release::Unanswered(queue)` を release queue に積む。
  release queue の要素は `ObjId` から `enum Release { Value, Unanswered }` にした。
* 掃除は `Value` なら `gc_unregister` だけ、`Unanswered` なら「印を付けて `close` して
  `gc_unregister`」。

`answered` の旗は、捨てたときに閉じるか閉じないかを分けるために要るが、ついでに
**2 度目の答えを断る**ことにもなる。これまでは 2 度目の `answer` がそのまま「もう登録を外した
キュー」に push していた。`gc_unregister` は同じ番号の最後の登録を 1 つ外すだけ
（SabiRuby 0.6.1 `vm.rs:2660`、`rposition` + `swap_remove`）なので、回収された後にその番号が別の
オブジェクトに使い回されていれば、**他人の登録を外す**ことになる。`Drop` 側も同じで、答えた後の
`Request` の `Drop` が閉じに行けば別のキューを閉じかねない。旗が要るのはそのためで、2 度目を
`warn!` 1 行で断るのはそこから出てくる振る舞いである。これは計画書に書かれていない振る舞いの
変化なので、報告に明記する。

`Held` の removal hook（`release_held`）は消した。`Held` が外れれば中の `Request` が落ち、落ちた
`Request` が自分で片付くので、hook が `gc_unregister` するともう一度外すことになる。しかも hook は
その場で外し、`Drop` の方は次のフレームの掃除で閉じるので、その間に回収されて番号が使い回される
窓ができる。**片付けの場所を 1 つにする**方が安全である。

### 3.3 待っている側にどう例外を届けるか

ここがいちばん考えたところ。`Task::Queue#close` は待っているタスクを全部起こし、`pop` は nil を
返す（mruby-task の意味。`docs/worklog/2026-09-16-bridge-followups.md` の 108 行付近）。
購読（`Rubevy::Unsubscribed`）では、`subscribe` が返すキュー 1 つに `Rubevy::Subscription` を
extend して `pop` を包んでいる。問いのキューで同じことをするには 3 案あった。

1. **`Rubevy.ask` のたびに extend する**（購読と同じ形）。— `Rubevy.ask` は `e[:Transform]` も
   `Rubevy.find` も `next_frame` も通る**いちばん熱い道**で、問い 1 つごとに特異クラスを 1 つ作り、
   `pop` に Ruby のフレームを 1 枚足すことになる。答えられる問い（ほぼ全部）のために払う費用ではない。
2. **`Task::Queue` の子クラスで作る**。— `Vm::task_queue_new` はクラスを選べないので `new` を自分で
   funcall することになり、`pop` のフレーム 1 枚は同じく全部の問いが払う。
3. **閉じる直前に、そのキュー 1 つにだけ extend する。** — 答えられる問いは何も払わない。

3 にした。ただし包むのは `pop` ではなく **`__pop_try`**。待っているタスクは**すでに `pop` の中に
いる**: mruby-task の `Task::Queue#pop`（`ref/mruby/mrbgems/mruby-task/mrblib/queue.rb`）は
`__pop_try` を `WAIT_RETRY` でなくなるまで呼ぶ Ruby のループで、`close` で起こされたタスクは
そのループの中で `__pop_try` をもう一度呼ぶ。後から extend した `pop` は次の `pop` からしか
効かないが、`__pop_try` は起きた直後の呼び出しから効く（SabiRuby にメソッドのインラインキャッシュは
無い — `ScriptWorld::irep_of` の rustdoc が 0.5.2 について書いているとおりで、実際テストが通る）。
`Rubevy::DroppedQuestion#__pop_try` は `closed? && empty?` なら `Rubevy::Unanswered` を上げ、
そうでなければ `super`。

**`__pop_try` は gem の内側の名前**である点は弱みとして書いておく。SabiRuby 0.7.0 で待ち方が
変わる（段階 B）ので、そこで `pop` がネイティブになるなどすれば、この仕掛けは黙って nil に戻る。
`tests/unanswered.rs` の 3 本（自分のタスク・子タスク・後から `pop`）がそれを捕まえるように書いて
ある。SabiRuby の main（`2fe974e`）にはまだ `__pop_try` があることは確かめた
（`src/builtins/ext_task.rs:869`、`src/mrblib/task.mrb` にも名前が入っている — 0.6.1 の
crate の `task.mrb` も同じ）。

例外は `Rubevy::Unsubscribed` を使い回さず、**新しい `Rubevy::Unanswered`** にした。原則は
「rescue する側が意味で選べること」。購読の終わりを rescue して静かに終わる handler
（games の 3 つの prelude が `rescue Rubevy::Unsubscribed` を書いている）が、断られた問いまで
黙って飲み込むのは別の話で、しかも `Unsubscribed` の文言（"the subscription ended"）は問いに
対しては嘘になる。どちらも `StandardError` の子で、`rescue => e` では両方捕まる。

extend してから close する順にしたのは、close が起こしたタスクが次に走るときには印が付いて
いなければならないから。掃除は `RubevySet::Deliver` で、タスクが走るのは後の `Tick` なので今は
順序の問題にならないが、そうならないように書いた。

### 3.4 数え方の変化

`release_dropped_values` の戻り値は「放した値の数」から「放したオブジェクトの数」になった
（答えずに捨てた問いのキューも数える）。`tests/ask_value.rs` の 3 本がこの数を見ていたので、
期待値を 1 ずつ増やし、メッセージに「キューも」と書いた。`a_request_that_is_never_answered_still_releases_its_value`
は 1 → 2（Hash とキュー）、`numbers_strings_and_entities_keep_their_fast_paths` は 0 → 1、
`a_cloned_request_holds_the_value_until_the_last_clone_is_gone` の最後は 1 → 2。

`tests/held.rs` は 1 本も変えずに通った。`registered` が 0 や 1 に戻るのが 1 フレーム遅くなる
（hook がその場で外していたのが、次のフレームの掃除になる）が、どのテストも `frames(3)` や
`until` で待っているため。despawn のテストの doc コメントだけ「removal hook が」を直した。

## 4. R1: スクリプトの止め方 — `stop_script`

### 4.1 文書と実物のずれ

`ScriptTask` の rustdoc は「Removing it (or despawning the entity) stops the task」、
`replace_script` の rustdoc は「To **stop** a script instead of replacing it, remove its
`ScriptTask` or despawn the entity; there is nothing else to do」、`host-api.md` の
「Replacing and removing a script」は「**Stopping** a script is still just removing its
`ScriptTask` or despawning the entity: there is no function for it because there is nothing else
to do」と書いていた。実物は、`start_scripts` の `PendingScripts`（`Without<ScriptTask<M>>,
Without<ScriptDone<M>>`）が `Script` の残った実体を拾い、**次のフレームで頭から**走らせる。
止まるのはタスクで、スクリプトではない。

これは held-requests の worklog の気づいた点 1 で書かれていて、ある組み込み先でも実際に踏まれた
（「タイトルへ」の後、`ScriptTask` だけを外した場面のスクリプトが次のフレームで頭から流れ直した。
その組み込み先は `Script` も外して逃げている）。`tests/stop.rs` の
`removing_the_task_alone_starts_the_script_again` がその振る舞いをそのまま固定している — 頭の行が
`Rubevy.ask('start')` のスクリプトから `ScriptTask` を外すと、`start` が 2 回目に来る。

「`ScriptTask` を外したら止まる」ように振る舞いを変える案（`ScriptTask` の removal hook が
`ScriptDone` を入れる、など）は採らなかった。`replace_script` がまさに「`ScriptTask` を外して
`Script` を入れる」で成り立っていて、`tests/replace.rs` と `restart_burst.rs` もその道を通る。
**振る舞いは正しい（再起動の部品）、文書と口が足りない**、と読んだ。

### 4.2 口の形をどう決めたか

候補は計画書が挙げた 2 つと、もう 1 つ:

1. `ScriptWorld::stop(...)` — `ScriptWorld` は resource なので `Commands` を持たない。止めるには
   `Script` を外す（構造の変更）必要があり、resource のメソッドからはできない。**形の上で無理**。
2. `commands.entity(e).stop_script()`（`EntityCommands` の拡張 trait） — できるが、このクレートで
   同じ種類の操作をしている口は **`replace_script(&mut Commands, Entity, Script<M>)` という自由関数**
   で、止めるのはその「新しいスクリプト無し」版である。
3. **`stop_script(&mut Commands, Entity)`** — `replace_script` の隣に同じ形で置く。

原則は「既存の API の流儀に合わせる」で、いちばん近い既存の口は `replace_script` なので 3。
rustdoc で `replace_script` を読んだ人が隣に見つけられる形である。

VM の名前札 `M` だけが問題になる。`replace_script` は引数の `Script<M>` から `M` が決まるが、
`stop_script(commands, entity)` には `M` を運ぶ引数が無く、Rust は式の中で型引数の既定値に
落ちない（`Script::new` と `Script::for_vm` が 2 つある理由として rustdoc にすでに書いてある）。
既存の流儀は **`hold_requests` / `hold_requests_for::<M>`** と `Script::new` / `Script::for_vm`
なので、`stop_script`（最初の VM）と `stop_script_for::<M>` の 2 つにした。

既存の公開 API は壊していない（足しただけ）。

### 4.3 止めるときに何を外すか

`stop_script_for::<M>` は `ScriptTask<M>` → `Script<M>` → `ScriptDone<M>` → `ScriptStartFailed<M>`
→ `Held<M>` の順に外す。

* **`ScriptTask` が最初。** removal hook（`stop_removed_task`）は `ScriptDone` があるかどうかで
  「すでに手放したタスクか」を見るので、その時点で `ScriptDone` がまだ付いていなければならない
  （`replace_script` と同じ順）。hook がタスクを terminate し、購読を閉じる。
* **`ScriptDone` も外す**ことにした。残すと、後で `Script` を入れても `PendingScripts` が
  `Without<ScriptDone>` で拾わず、黙って始まらない。止めた実体を「一度もスクリプトを持たなかった
  実体」と同じにしておくのが、後で何かを入れたときにいちばん驚きが少ない。
  （別案として「`Script` を残して `ScriptDone` を付ける」— 何を走らせていたかは残る — も考えたが、
  それだと `ScriptDone` の意味が「終わった」と「止められた」の 2 つになり、後から `Script` を
  入れ直しても始まらない罠が残る。）
* `ScriptStartFailed`（非公開）も外す。読み込めない `.mrb` で止まっていた実体を止めた後に、
  資産の変更で勝手に始まらないように。
* `Held` は R2 の後なので、外せば中の `Request` が落ち、次の掃除でキューが閉じ、`Task.new` の
  子は `Rubevy::Unanswered` で巻き戻る。

`ScriptEnded` は送らない。スクリプトは終わったのではなく、ゲームが止めた。ゲームは知っている。

**止まらないもの**も rustdoc と `host-api.md` に書いた: 何も待っていない `Task.new` の子
（`loop` や `sleep` の中にいるもの）。SabiRuby の `Task` は親を記録しない（`TaskData` に親が無い
ことは `docs/worklog/2026-09-16-bridge-followups.md` §2 が確かめている）ので、見つける手がかりが
無い。despawn でも同じで、これは今回の変更の前からの穴である（気づいた点に書く）。

### 4.4 確かめたこと

`tests/stop.rs`（5 本）:

* `a_stopped_script_does_not_start_again` — 止めた後 20 フレーム、`tick` は増えず、`start` は 1 回
  のまま、`ScriptTask` は作り直されず、登録は 0。
* `removing_the_task_alone_starts_the_script_again` — 上のとおり、手で `ScriptTask` だけを外すのは
  再起動である、ということを固定する。
* `what_it_was_waiting_on_goes_with_it` — 購読で待つ子は `Rubevy::Unsubscribed`、held の問いで待つ
  子は `Rubevy::Unanswered` を聞いて終わり、登録は 0 に戻る。
* `a_script_that_ended_is_stopped_and_the_entity_can_have_another` — 終わったスクリプトも止められ、
  `ScriptDone` が外れ、終わったタスクの登録は 2 度外されず、後から入れた `Script` は始まる。
* `stop_script_for_stops_one_vm_and_not_the_other` — 1 つの実体に 2 つの VM のスクリプト。
  `stop_script_for::<Mods>` は Mods の方だけを止める。

文書は `ScriptTask` と `replace_script` の rustdoc、`Held` の片付けの表（rustdoc と `host-api.md`）、
`host-api.md` の「Replacing and removing a script」と Events の規則、`README.md` の 1 行を直した。

## 5. R1 の続き: 手で `ScriptTask` を外した再起動が、古い問いを引き継いでいた

`tests/stop.rs` を書いていて、「`ScriptTask` を手で外す」道を `Held` と組み合わせたらどうなるかを
スクラッチのテストで見た（`Rubevy.ask('wait', 1).pop` で待っているスクリプトの `ScriptTask` だけを
外し、4 フレーム回す）。結果は `Held` の長さが **2**。死んだタスクの問いと、再起動した新しい
スクリプトの問いが 1 つの `Held` に並んでいた。

原因は順序である。`Held` の表は「the game removed `ScriptTask` by hand → the next tick, which is
where a `Held` with no live script is swept」と言っていたが、`start_scripts` は `RubevySet::Deliver`、
掃除（`drain_commands` の頭）は `RubevySet::Tick` にあり、その間に `Commands` が反映される。
`Script` が残っていれば、掃除が見る時点で新しい `ScriptTask` がもう付いていて、`has_task` が真、
`ScriptDone` も無いので**生きているスクリプトとして素通り**する。新しいスクリプトの最初の問いは
その後ろに積まれ、`Held::answer` は古い方（死んだタスクのキュー）から答える。held-requests の
テスト `a_script_stopped_by_hand_is_swept` は `Script` も外していたので当たらなかった。

これは R1 以前からの不具合だが、R1 で「`ScriptTask` を外すのは再起動である」と文書に書く以上、
その再起動が壊れているのを表に「片付く」と書いたままにはできないので、直した。
`ScriptTask` の removal hook（`stop_removed_task`）が、タスクを止めて購読を閉じた後に
`world.commands().entity(e).try_remove::<Held<M>>()` を積む。タスクが止まるならそのタスクの問いも
終わり、という 1 か所にまとめた形で、despawn（どのみち消える）・`replace_script` と `stop_script`
（自分でも外す）では何もしない。`try_remove` なのはそのため。`drain_commands` の掃除の
「生きたスクリプトが無い」条件は残した（守りとして。コメントをそう直した）。

`tests/held.rs` に `a_restart_by_hand_does_not_inherit_the_old_question` を足した。直す前は
`left: 2 right: 1` で落ち、直した後は `Held` の長さ 1、登録は新しいタスク・そのキュー・その Hash の
3 つ。表（rustdoc と `host-api.md`）の行は「its removal hook, at once」に直した。

**これは計画書の R1〜R4 に書かれていない直し**なので、別のコミットにしてある。要らなければ
そのコミットだけ戻せる（戻すと表の行も元に戻る）。

## 7. 気づいた点

1. **`ScriptEnded::at` と `ScriptStats` は、`require` したファイルのフレームにも前置きの引き算を
   する。** `authors_place` はファイル名を見ないので、`require` された `helper.rb` の 50 行目で
   待っているスクリプトの `prelude_lines` が 30 なら「helper.rb:20」と答え、10 行目なら外す。
   正しくは「スクリプト自身のファイル（いちばん外側のフレームのファイル）だけに引き算をする」。
   R4 では `at` と同じ線を引くことを優先して、この穴も同じにした。games は今 `require` と前置きを
   同時に使っていないので当たっていない。**属する先**: rubevy（`src/lib.rs` の `authors_place` /
   `authors_line` / `ScriptWorld::stats`）。
2. **何も待っていない `Task.new` の子は、`stop_script` でも despawn でも止まらない。** SabiRuby の
   `Task` が親を持たないので、rubevy からは見つけられない。子は実体を持ち続け、問えば「生きた
   スクリプトの無い問い」になる。直すなら VM に親を持たせる（SabiRuby）か、`Task.new` の prelude の
   上書きで rubevy がタスクの一覧を実体ごとに持つか。**属する先**: rubevy と VM（SabiRuby）。
   rustdoc と `host-api.md` には今の振る舞いとして書いた。
3. **`DroppedQuestion` は mruby-task の内側の名前 `__pop_try` に依っている。** SabiRuby 0.7.0 で
   `pop` の作りが変われば黙って nil に戻る。`tests/unanswered.rs` が捕まえるので、段階 B で
   `cargo test` が通ればよい。**属する先**: 段階 B の確認。
4. **games の `Cargo.lock` は rubevy を git の `c9b52a3`（0.0.1）で固定している。** rubevy 0.1.0 は
   crates.io に出ているが games は上がっておらず、手元の patch もそのままでは効かない（§6.2）。
   **属する先**: rubevy_games（段階 D、0.2.0 に上げるとき）。
5. **`answer_value` は 2 度目の答えでも閉包を走らせる**（値を作ってから、答えを断る）。害は無い

6. **CHANGELOG に 0.2.0 の節はまだ無い。** 振る舞いの変化（2 度目の答えを断る、捨てた問いを
   閉じる、`ScriptStats` の行、`release_dropped_values` の数え方、`Held` の removal hook が無く
   なった）は 0.2.0 の節に「Coming from 0.1.0」として書く材料。**属する先**: 公開の段階 E。

## 8. 本体の指示で足したもの（気づいた点 1・2・5・6）

本体から「0.2.0 をきれいにしたいので、気づいた点の 1・5 を直し、2 を backlog に、6 を CHANGELOG に」
という指示があった。`6d6e6b7` は残す、との返事も受けた。3（`__pop_try`）は段階 B で見る

**気づいた点 1 — `require` したファイルの行。** `authors_place(line, prelude_lines)` を
`authors_places(frames, prelude_lines)` に置き換えた。フレームの列を受け取り、**いちばん外側の
