## 1. 前提 — SabiRuby の R2 が写しで確かめてあった

SabiRuby 0.8.0 は同じ日に公開された（`sabiruby` 0.8.0、`sabiruby-compiler` 0.5.0、`sabiruby-serde` 0.4.0、tag `v0.8.0` = `7f74cd1`）。
公開の前に SabiRuby の R2（SabiRuby `docs/worklog/2026-10-19-release-0.8.md` の 8 節）が、この repo を `git archive` した写しの
`Cargo.toml` の 5 行だけを上げて `[patch.crates-io]` で手元の SabiRuby に向け、`cargo check` 警告 0、`cargo test --workspace` 249、
`--all-features` 251 を取っていた。0.8 の壊す API（`HashData`、`InstanceKind`、`HeapObject`、`CallInfo`、引数の宣言）は
どれも rubevy が呼んでいないので、コードの変更は要らない、というのがその結論。今回はそれを本物の木で、crates.io の 0.8 に対してやり直した。

## 2. 変えたもの

- `Cargo.toml` の 5 行（R2 の表のとおり）: `[dependencies]` の `sabiruby "0.7"→"0.8"`・`sabiruby-compiler "0.4"→"0.5"`、
  `[dev-dependencies]` の `sabiruby "0.7"→"0.8"`（`macros`）・`sabiruby-compiler "0.4"→"0.5"`・`sabiruby-serde "0.3"→"0.4"`。
- 同じファイルのコメント 3 か所: `rust-version` の出どころ（「sabiruby 0.8 says 1.85」。0.8.0 の `rust-version` も 1.85 なので
  `rust-version = "1.95.0"` は動かない）、VM の下限の理由（0.8.0 が VM の壊すリリースであること、rubevy は触らないが `^0.7` だと
  アプリが 0.8 を名指ししたときに VM が 2 つになること。0.7 で入って rubevy が今も使うもの — `hash_get` の `Result` と
  ブロックの中で待てること — は括弧で残した）、compiler の対応（0.5 が 0.8.x の VM と組む。SabiRuby `docs/design/compiler.md` の 196 行）。
- `version`: `rubevy` 0.2.1 → 0.3.0、`rubevy-build` 0.2.0 → 0.3.0（3 節）。`cargo update -p sabiruby -p sabiruby-compiler -p sabiruby-serde` で
  lock を上げた（`sabiruby v0.7.0 -> v0.8.0`、`sabiruby-compiler v0.4.0 -> v0.5.0`、`sabiruby-serde v0.3.0 -> v0.4.0`。`sabiruby-macros` は 0.1.1 のまま）。
- CHANGELOG を `## 0.3.0 — 2026-10-19` に切った。README の Install（`rubevy "0.3"`、VM 0.8、compiler 0.5、「The version is 0.3」）。
  `outlook.md`／`outlook.ja.md` の公開の表に 0.3.0 の行。

**README の Install は 0.2.0 のときから古かった。** 「The VM comes from crates.io with it: `sabiruby` 0.6」「`sabiruby-compiler` 0.3」
「The version is 0.1」のまま、0.2.0 の公開 commit（`e6deab8`）は `rubevy = "0.2"` の 2 行しか直していなかった。crates.io に出る文面なので
今回まとめて直し、CHANGELOG にも 1 行書いた。

## 3. `rubevy-build` を 0.3.0 にした理由

中身は変わらず、依存も無い（std だけ）。依頼の文面は「変わる所が無ければ据え置く」だったが、この repo の考え方を読むと揃える方になる:

- `rubevy-build/Cargo.toml` のコメントが「`rubevy` と同じ数。1 つの repo・1 つの tag・1 つの CHANGELOG で一緒に出る。
  `rubevy-build` 0.1.0 は `rubevy` 0.1.0 と組むもの」と慣習を書いている（要件ではなく読む人のための慣習、とも書いてある）。
- 0.2.0 は、中身の変わらない `rubevy-build` を `rubevy` と一緒に 0.2.0 にした（CHANGELOG の 0.2.0 の節「unchanged, moved with `rubevy`
  as the two always go together」）。
- patch の 0.2.1 では据え置いた（CHANGELOG「`rubevy-build` stays at 0.2.0 (no change)」）。

つまり慣習は「minor を揃え、patch は揃えない」と読める。0.3.0 で据え置くと、`rubevy` 0.3.0 と組むのが `rubevy-build` 0.2.0 になり、
コメントの慣習のほうを書き直すことになる。公開の費用は 1 回の `cargo publish` で、games は git で指しているので
`cargo update -p rubevy-build` で同じように付いてくる。据え置きに戻すなら `rubevy-build/Cargo.toml` の 1 行と CHANGELOG の 1 文で済む。

## 5. 公開の順（本体）

```
git push origin main
cargo publish --dry-run -p rubevy-build && cargo publish -p rubevy-build   # -> rubevy-build 0.3.0
cargo publish --dry-run -p rubevy       && cargo publish -p rubevy         # -> rubevy 0.3.0
git tag -a v0.3.0 -m "rubevy 0.3.0: on SabiRuby 0.8.0 (sabiruby 0.8, sabiruby-compiler 0.5); rubevy-build 0.3.0 (unchanged)" <この commit>
git push origin v0.3.0
```
