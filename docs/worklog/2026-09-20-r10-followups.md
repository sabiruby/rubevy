# 2026-09-20 R10 が R11 に送った 3 つの宿題

計画 `docs/plans/generalize-plan.md` 7 章の「09-20 R10」の 2 行と、6 章の「既定値（R10）」の行。
R10 は数の一覧（`docs/numbers.md`）を作る過程で 4 つの気づきを残し、そのうち 3 つを
「R11 のついでに直す」と計画に書いた。R11 の本体（`Rubevy.next_frame`、
`docs/worklog/2026-09-20-next-frame.md`）とは別のコミットにしてある。

**既定値は 1 つも動かしていない。** 動かすかどうかは著者判断（CLAUDE.md）。

## 1. 計測器が既定値を写していた

`examples/how_many_scripts.rs` の `Limits::Default` は
`scripts.budget = 200_000; scripts.frame_time = Some(Duration::from_millis(8))` と直書きで、
行の名札 `"default(200k/8ms)"` が同じ数の 3 度目の写しだった。**既定値が動いた日に、
`default` と名乗る行が既定でない設定を測る。**

直し方は「プラグインが建てた `ScriptWorld` から読む」。`Defaults::of(&app)` が
`budget` と `frame_time` をそのまま読み、4 つの行は全部その 2 つの掛け算・割り算になった。

| 行 | 前 | 後 |
|---|---|---|
| `default` | 200,000 / 8 ms（直書き） | 既定そのもの |
| `generous` | 100,000,000 / なし | 既定の予算 × `GENEROUS`（500）/ なし |
| `tight` | 200,000 / 1 ms | 既定の予算 / 既定の `frame_time` ÷ `TIGHT`（8） |
| `clocked` | 100,000,000 / 1 s | 既定の予算 × 500 / `FRAME` × `NEVER_DUE`（60） |

倍率と除数は**前から rustdoc に書いてあった言葉**（「五百倍」「1/8」「時計を読むこと以外は
`generous` と同じ」）をそのまま数にしたもので、新しく選んだ数ではない。

名札は実際に使った数から組む（`Limits::name`）。**既定のままなら字は今までと同じ**になるように
した — `docs/verification/scale.md` の表が行名で引けるからで、そのために
`clocked` の 60 フレーム（1.00000002 s）を `1s` と印字する丸めを表示側だけに入れた。
`cargo run --release --example how_many_scripts -- 6 1 25 0.004` で 5 行とも
`default(200k/8ms)` / `generous(100M/none)` / `tight(200k/1ms)` / `clocked(100M/1s)` と出ることを
確かめた。

### 「Every one of them is an argument」

計測器 2 本の冒頭がそう書いていたが、正確ではなかった（R10 の気づき 2）。**小さい方**を選んで
文を実物に合わせた — ただし `how_many_scripts` の台数と sleep だけは引数で任意の値を
渡せるようにした。理由は、一覧に無い数を渡すと `continue` で全部飛ばされて**1 行も出ずに終わる**
からで、これは「測ったのに何も出ない」に見える。`-- 90 3 500 0.01` が 500 台を測るようになった。

`how_many_subscribers` の方は表の形（購読者数・1 フレームの件数・上限の列）を引数にしていない。
1 つのセルは同じ行の他のセルと並べて初めて読めるので、この計測器が出すのは表かモードであって
セルではない、と書いた。

## 2. 深さを超えた書きの断り文句が深さの話をしなかった

`max_depth` を超える Hash は**まず VM から読み出す側**（`reflect::read_ruby`）で切られていて、
境界の 1 つ先のエントリは鍵も値も `RubyData::Nil` になって書く側に届く。だから書く側の
`apply_at` にある `too deep` には（この道からは）決して届かず、スクリプトが
`Rubevy.rejected_writes` で読むのは

    b.c: a field name must be a Symbol or a String

だった。場所は正しいが、文は nil のことを言っていて深さのことを言っていない。

直した形: **読み出す側が境界で `RubyData::TooDeep` を返す**（nil と区別できる第 3 の状態）。
書く側は (1) 値がそれなら、(2) 鍵がそれなら、(3) 自分の深さが尽きたなら、の 3 か所で同じ文を言う。

    b.c: deeper than max_depth (2), so nothing under it was read or written

数（app が設定した `max_depth`）を文に入れるために、書きの問題を集める入れ物を
`Vec<String>` から `Problems { max_depth, list }` に替えた。`problems.push(…)` の呼び出しは
そのままで、足したのは `problems.too_deep(path)` の 1 メソッドである。数を文に入れたのは、
「深すぎる」とだけ言われても**どの数**かが分からないからで、しかもそれは app が動かせる設定である
（`ScriptWorld::set_max_depth`）。

`tests/max_depth.rs::a_shallower_setting_stops_a_write` の期待を、前置き
（`starts_with("b.c: ")`）から**文そのもの**に変えた。テストのコメントに書いてあった
「なぜ nil の話になるのか」の説明も、新しい振る舞いの説明に書き直した。

**消えたエンティティへの書き**（R10 の同じ行の後半）は見送った — 計画どおり。

## 3. 「選び方」を文書に

計画 6 章の「既定値（R10）」の行。**既定値は動かさない**が、外の利用者が自分の数を選べるように
`docs/host-api.md` の「Time」に「Choosing `budget` and `frame_time` for your game」を足した。
手順は 3 つ: (1) 自分のゲームの**命令/ms** を `FrameStats`（`instructions` と `time_ns`）で測る、
(2) 目標フレーム時間のうちスクリプトに渡す分を決め、**VM の本数で割って** `frame_time` にする、
(3) その時間が買える命令数を `budget` にする。60 Hz を例に使った。

**「8 ms は 60 Hz の半分」「50 ms は 3 フレーム」は書いていない。** これは R10 の担当が
見つけた一致であって記録ではないので、出どころとしては書かない（`numbers.md` の「不明」もそのまま）。
例として 60 Hz の数を使うのは別の話である。

### 引用元を確かめたら、計画書の要約と逆だった

計画書の R11 の行は「rubevy の計測器は約 32,800 命令/ms で予算が先に効き、**箱庭は約 9,300
命令/ms で時計が先に効く**」と要約していた。引用元を 2 つとも読んだ。

* **32,800 命令/ms**: `docs/worklog/2026-09-17-sync-reads.md` §5.1 の表。予算 200,000 を
  6.10 ms で使い切っている（同じスクリプトを `frame_time = None` で走らせても読めた回数が
  同じ 2667 なので、止めたのは時計ではなく予算）。200,000 / 6.10 ms = 32,787。**予算が先** ✓
* **9,300 命令/ms**: rubevy_games `garden/src/main.rs` の `install_world_answers` のコメント。
  ただしそこにはこう書いてある — 世界の VM は `budget = 45_000` で、その率では約 4.8 ms、
  `frame_time` は rubevy の 8 ms のままなので「**the instruction count is what bites first**」。
  つまり箱庭の世界の VM も**予算が先**である。

計画書の要約が指していたのはおそらく箱庭の**もう 1 本の VM**（生き物の方。rubevy の既定
200,000 のまま）で、9,300 命令/ms なら 200,000 は約 21 ms、既定の `frame_time` 8 ms を大きく
超えるので**時計が先**になる。これは引用した率での計算であって測定ではないので、文書では
「同じ計算を rubevy の既定の予算に当てると」と書き方を分けた。計画書の 1 行は直していない
（計画書は本体のもの）。報告に書く。

この食い違いは文書としては幸運だった。**同じ 2 つの既定値が、ゲームによってどちらが先に効くかが
変わる**という、まさに「自分で測れ」の実例になったので、そう書いた。
