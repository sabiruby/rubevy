## 最初に確かめたこと — derive がジェネリクスに足す境界（§6.1）

計画書の罠 §6.1 は「derive が `M: Clone` などを勝手に足すので手で書け」。
これは標準の derive（`Debug` / `Clone` / `Copy` / `PartialEq` / `Eq` / `Hash`）の話で、
**Bevy の derive は違う**ことを先に確かめた。`bevy_ecs_macros-0.19.1` と `bevy_macro_utils-0.19.1` を読むと:

* `#[derive(Message)]`（`src/message.rs:11`）は where 句に `Self: Send + Sync + 'static` を足すだけ。
* `#[derive(Component)]` / `#[derive(Resource)]`（`bevy_ecs_macro_logic/src/component.rs:271`）も同じく `Self: …` だけ。
* `#[derive(SystemSet)]` は `bevy_macro_utils/src/label.rs:79` で
  `Self: 'static + Send + Sync + Clone + Eq + Debug + Hash` を足す。

つまり Bevy の derive はどれも `M` に境界を足さない。手で書く必要があるのは標準の derive のほうだけで、
`Script` / `ScriptTask` / `ScriptEnded` の `Debug`・`Clone`・`Copy`、`RubevySet` の 6 つを書き下ろした。
Bevy 側の derive はそのまま残せた。

## いちばん大きな発見 — 既定型引数は「式の位置」では効かない

計画書は「既定型引数のおかげで既存コードは 0 行で通る」と書いている（§4 の表、§9）。
これは**型の位置では正しいが、式の位置では正しくない**。Rust は式の中で型引数の既定値に落ちてくれない
（`default_type_parameter_fallback` は今も unstable）。スクラッチパッドで最小の例を作って確かめた:

```rust
pub struct Script<M = ()> { … }
impl<M: 'static> Script<M> { pub fn new(p: u8) -> Self { … } }
fn main() { take(Script::new(1)); }
```

```
error[E0282]: type annotations needed
 | take(Script::new(1));
 |      ^^^^^^^^^^^ cannot infer type of the type parameter `M` declared on the struct `Script`
```

同じことを 4 つの形で試して、どれが通りどれが通らないかを表にした（`rustc` 単体、bevy なし）:

| 書き方 | 定義 | 結果 |
|---|---|---|
| `Script::new(h)` | `impl<M> Script<M> { fn new }` | **E0282**（`M` が決まらない） |
| `Script::new(h)` | `impl Script<()> { fn new }` | 通る（候補の自己型と単一化して `M = ()`） |
| `Plug::default()` | `impl<M> Default for Plug<M>` | **E0282** |
| `Plug::default()` | `impl Default for Plug<()>` | 通る |
| `E::A`（enum の枝） | `enum E<M = ()> { A, … }` | **E0282**。枝には逃げ道がない |
| `Set::Answer`（関連定数） | `impl Set<()> { const Answer }` | 通る |
| `Set::<Mods>::answer()` | `impl<M> Set<M> { fn answer() }` | 通る |

`Script::new(handle)`、`RubevyPlugin::default()`、`.in_set(RubevySet::Answer)`、`ScriptWorld::QUEUE_LIMIT` は
どれも tests・examples・サンプルゲームが**実際に書いている式**なので、ここが通らなければ
「ゲームを 1 行も変えない」という受け入れ条件が壊れる。そこで段階 0 の設計をこう決めた:

* **`Script::new` は `impl Script<()>`**（1 本目の VM の版）。名札つきは `Script::<Mods>::for_vm(handle)` という
  別名にした。同じ名前で総称版と具体版の両方を置くことはできない（重なる inherent impl は E0592）。
* **`impl Default for RubevyPlugin<()>`**。`with_asset_root` のほうは**総称のまま**にできた。
  ゲームもテストも `with_asset_root` を素で呼んでいる場所が 1 つも無く（`RubevyPlugin::default()` だけ）、
  総称にしておけば計画書 §4.3 の綴り `RubevyPlugin::<Mods>::with_asset_root("assets/mods")` がそのまま通るから。
  代わりに 1 本目を素で `RubevyPlugin::with_asset_root("assets")` とは書けなくなった
  （`RubevyPlugin::<()>::with_asset_root(…)` と書く）。README:85 のコメントがこの綴りなので、段階 3 の docs 更新で直す。
* **`RubevySet` は enum をやめて struct + 関連定数**にした。計画書 §4.1 は
  `pub enum RubevySet<M = ()> { Deliver, Tick, Answer, …PhantomData }` と書いているが、上の表のとおり
  **enum の枝は式の位置で既定値に落ちない**ので、これだと `.in_set(RubevySet::Answer)` が全部 E0282 になる
  （ゲーム側だけで 10 か所以上）。中身は `SetKind`（private な 3 値 enum）を持つ struct にして、
  `impl RubevySet<()>` に `Deliver` / `Tick` / `Answer` の定数を、`impl<M> RubevySet<M>` に
  `deliver()` / `tick()` / `answer()` を置いた。既存の綴りは 1 文字も変わらず、名札つきは
  `RubevySet::<Mods>::answer()` になる。`#[allow(non_upper_case_globals)]` が 1 つ増えるのは、
  定数が enum の枝の名前をそのまま引き継いでいるから。
* **`ScriptWorld::QUEUE_LIMIT`** は総称の impl に置くと `tests/events.rs:241` が E0282 になった
  （これは実際に最初のビルドで出た。上の表を先に作っていたので原因はすぐ分かった）。
  値は VM ごとに変わるものではないので、モジュールの定数 `QUEUE_LIMIT` にして、
  `impl ScriptWorld<()>` からその名前で公開した。内部の `make_room` は定数を直接読む。

捨てた案: 同じ名前で「素の呼び出しは `()`、turbofish つきは総称」を両立させる方法として、
総称版をトレイトのメソッドにする手（inherent が優先されるので両方成立する）を検討したが、
利用者側に `use rubevy::ScriptFor;` を強いるうえ、なぜそうなっているかが読んで分からない。
名前を 1 つ増やす（`for_vm`）ほうが正直だと判断した。

## コンポーネントのフックとジェネリクス（§6.2）

計画書は「`#[component(on_remove = stop_removed_task)]` が `stop_removed_task::<M>` を取れるかは要確認、
だめなら observer（`app.add_observer(on_remove_script_task::<M>)`）に替える」としていた。
**フックのまま通った**ので、observer の代案は採らなかった。理由は 2 つ:

1. `bevy_ecs_macro_logic/src/component.rs:519` の `HookAttributeKind` は属性の右辺を `Expr` として読み、
   `Expr::Path` を受け付ける。`stop_removed_task::<M>` はターボフィッシュつきのパス式なので `Expr::Path` に入る。
   生成されるフック関数は `impl … Component for ScriptTask<M>` の**中**に置かれるので、`M` はそこで見えている。
2. `stop_removed_task::<M>` は `M: 'static` を要求する。impl の where 句には derive が足した
   `Self: Send + Sync + 'static` しか無いので、そこから `M: 'static` が導けるかが分かれ目だった。
   これも最小の例で確かめてから書いた:

   ```rust
   struct S<M>(PhantomData<fn() -> M>);
   fn g<M: 'static>() {}
   impl<M> Tr for S<M> where Self: Send + Sync + 'static { fn f() -> fn() { g::<M> } }
   ```

   通る。`Self: 'static` から `M: 'static` は出る。だから構造体の定義に境界を足す必要もなかった。

observer に替えなかったのは、挙動が同じで行数が増えるだけだから。フックは「このコンポーネントが外れたら」という
一点に結びついているので、`ScriptTask<M>` の定義のそばに書いてあるほうが読める。

## 境界は `M: 'static` だけにした

計画書 §5 は `impl<M: 'static + Send + Sync> ScriptWorld<M>` と例示し、§4.2 は
「`M` には `'static` 以外の境界を付けない」と書いている。**§4.2 を採った**。理由は 2 つで、
1 つは `PhantomData<fn() -> M>` にしたおかげで `ScriptWorld<M>` などの `Send`/`Sync` は
`M` によらず構造的に出るから（`Send + Sync` を要求しても得るものが無い）、
もう 1 つは上のフックで、`ScriptTask<M>: Send` から `M: Send` は**導けない**ので、
`stop_removed_task` に `M: Send` を要求すると通らなくなるから。
結果、名札は `struct Mods;` のような何も実装していない空の型でよく、`'static` でありさえすればよい。

## 項目 0 — `with_asset_root` を 1 本目に返す（`4d32569`、別コミット）

段階 0 の記録に自分で書いた借りを返す作業。段階 0 では `with_asset_root` を
`impl<M> RubevyPlugin<M>` に置いた。テストもゲームも `RubevyPlugin::default()` しか呼んでいなかったので
ビルドは通ったが、その代償に **1 本目を素で `RubevyPlugin::with_asset_root("assets")` と書けなくなっていた**
（`RubevyPlugin::<()>::with_asset_root(…)` になる）。README:85 のコメントがまさにその綴りなので、
このままだと README が嘘になる。式の位置で既定型引数に落ちないという段階 0 の発見は、
**「素で書ける入口は必ず `<()>` の impl に置く」**という規則として使うべきものだった。

そこで `Script::new` / `Script::for_vm` と同じ形に揃えた:

| 入口 | 置き場所 | 綴り |
|---|---|---|
| 1 本目・既定の root | `impl Default for RubevyPlugin<()>` | `RubevyPlugin::default()` |
| 1 本目・root 指定 | `impl RubevyPlugin<()>` | `RubevyPlugin::with_asset_root("assets")` |
| 名札つき | `impl<M: 'static> RubevyPlugin<M>` | `RubevyPlugin::<Mods>::for_vm("assets/mods")` |

`with_asset_root` の中身は `RubevyPlugin::<()>::for_vm(root)` を呼ぶだけにして、実体は 1 つに保った。
`RubevyPlugin` の rustdoc の例も `::<Mods>::with_asset_root` → `::<Mods>::for_vm` に直した（doctest なので
綴りが間違っていればテストが落ちる。これは段階 0 で 1 本増やした doctest がそのまま見張り役になった形）。

捨てた案: `with_asset_root` を 1 本目と名札つきの両方で使えるようにするために、名札つきだけトレイト経由にする
——段階 0 で一度検討して捨てた手だが、ここでもう一度考えた。やはり `use rubevy::PluginFor;` を利用者に強いるので、
名前を 1 つ増やすほうを採った。`for_vm` は `Script::for_vm` と対になっていて、
**「名札つきの入口はどれも `for_vm`」**という 1 行の規則で覚えられる。

この時点で §7.1 と §7.2 を通してからコミットした（結果は下の「確認」にまとめてある）。

## 項目 1 — `ScriptDone<M = ()>`

段階 0 の記録の最後に「後の段階へ」として残した穴。1 つのエンティティに `Script<A>` と `Script<B>` を
付けられる（計画書 §3 既定 6）のに `ScriptDone` は名札を持たないので、片方が終わっただけで
`tick_scripts` の `Without<ScriptDone>` が**両方**のタスクを見なくなり、
`stop_removed_task` の「もう手放した」判定も**両方**に効いてしまう。

`Script` / `ScriptTask` と同じ作りにした。`PhantomData<fn() -> M>` を 1 つ持ち、
`Debug` / `Clone` / `Copy` は手で書く（§6.1。derive だと名札自身に `Debug` などを要求してしまう）。
唯一ひっかかったのは**構築の綴り**で、`ScriptDone` は今まで unit struct だったから
`commands.entity(e).insert(ScriptDone)` と値として書けていた。フィールドが付くとそれができない。
式の位置の規則をそのまま当てて、`impl ScriptDone<()>` に `new()`、`impl<M: 'static> ScriptDone<M>` に
`for_vm()` を置いた。`new()` を引数なしで公開すると clippy の `new_without_default` が出るので、
`impl Default for ScriptDone<()>` も足してある（最初は `#[allow]` で黙らせたが、
警告を増やさないという条件を `allow` で満たすのは筋が悪い。`Default` があって困るものでもない）。

利用側は 3 か所だけだった: `stop_removed_task` の `world.get::<ScriptDone<M>>`、
`tick_scripts` の `Without<ScriptDone<M>>`、そして `insert(ScriptDone::<M>::for_vm())`。
ゲーム側（rubevy_games）は `.remove::<rubevy::ScriptDone>()` が 4 か所で、すべて**型の位置**なので
既定型引数が効き、1 行も変わらない。これは計画書が前提として書いていたとおりだった。

## 項目 2 — プラグインの二重登録（§6.3）

`RubevyPlugin::build` の `init_asset::<MrbAsset>()` と `init_asset_loader::<MrbLoader>()` は
名札に関係のない共有資源なので、2 本目のプラグインがもう一度呼ぶと何かが起きる。
「何が起きるか」を先に読んだ。`bevy_asset-0.19.1/src/lib.rs:639` の `init_asset` は

```rust
let assets = Assets::<A>::default();
…
self.insert_resource(assets)
```

で、**毎回まっさらな `Assets<A>` を作って差し替える**。つまり 2 本目のプラグインは、
1 本目の VM がすでに持っているハンドルの中身を丸ごと捨てる。`init_asset_loader` のほうは
`register_asset_loader` なので、`.mrb` を名乗るローダーが 2 つ並ぶ。

対策は計画書 §6.3 のとおり実体で判定する:

```rust
if !app.world().contains_resource::<Assets<MrbAsset>>() {
    app.init_asset::<MrbAsset>().init_asset_loader::<MrbLoader>();
}
```

`app.is_plugin_added::<RubevyPlugin<M>>()` が使えないのは、`RubevyPlugin<Mods>` と `RubevyPlugin<()>` が
別の型で、互いの登録が見えないから。`add_message::<ScriptEnded<M>>()` は `M` ごとに別の型なので触っていない。

**この直しが本当に効いているかを確かめるのに手間取った。** 最初に書いた `tests/two_vms.rs` は
ガードを外しても 7 本とも通ってしまう。理由はすぐ分かって、テストはプラグインを 2 つとも足し終えてから
アセットを追加するので、捨てられるものが何も無い。そこで**プラグインとプラグインの間でアセットを足す**
形を作った（`tests/vm_setup.rs` が「アプリを組み立てている途中で VM に触る」を実際にやっているので、
これは架空の使い方ではない）。使い捨てのテストを 1 本置いて測ると:

```
ガード無し: the second plugin threw the first VM's assets away  … FAILED
ガード有り: an_asset_added_between_the_two_plugins_survives     … ok
```

見えたので、使い捨てにせず `tests/two_vms.rs` の 7 本目として残した
（`the_second_plugin_does_not_throw_away_the_first_vms_assets`）。計画書が挙げた 6 項目は
スクリプトどうしの独立の話で、これだけはプラグインの話なのでテストの docstring にそう書いてある。
**指示は「6 項目を 1 本ずつ」だったので、この 7 本目は要らなければ落としてよい**（報告にも書いた）。

## 項目 3 — `RubevySet<M>` の独立

段階 0 で `RubevySet` は struct + 関連定数になり、プラグインは `RubevySet::<M>::deliver()` などで
`configure_sets` を呼んでいる。ここで一瞬心配になったのは、段階 0 で手書きした `Hash` と `PartialEq` が
**`self.which` しか見ていない**ことだった。`RubevySet::<A>::tick()` と `RubevySet::<B>::tick()` が
同じ集合と見なされたら、2 本の VM のフレームが 1 本の鎖に繋がってしまう。

`bevy_ecs-0.19.1/src/label.rs` を読んで決着した。Bevy はラベルを `DynEq` / `DynHash` 越しに比べていて、

* `dyn_eq`（29 行）は `downcast_ref::<T>()` してから比べる。型が違えば無条件に `false`。
* `dyn_hash`（51 行）は値のハッシュに **`self.type_id()` を混ぜる**。

つまり名札はハッシュにも同一性にも効いていて、手書きの `eq` が `which` しか見なくても正しい。
コードにその根拠をコメントとして残した（行番号つき）。実挙動のほうも、
`tests/two_vms.rs` が 2 本の VM それぞれの `RubevySet::<A>::answer()` /
`RubevySet::<B>::answer()` に答え手を置いて往復させているので、鎖が混ざっていれば通らない。

## 項目 4 — `tests/two_vms.rs`

名札は `struct A;` と `struct B;`。**どちらも 1 本目（`()`）ではない**のが狙いで、
こうしておけば「既定型引数に落ちたおかげで通った」という通り方がありえない。
名札は何も実装していない空の struct なので、§6.1 の「derive が境界を足す」を実際に踏む
（`Script<A>` の `Clone`、`RubevySet<A>` の `Hash`、`ScriptDone<A>` の `Copy` がすべて手書きである必要がある）。

書き方は既存の `tests/*.rs` に合わせた。`MinimalPlugins.set(ScheduleRunnerPlugin::run_once())` +
`AssetPlugin` でヘッドレス、`app.update()` を回して進める、スクリプトは
`sabiruby_compiler` でその場でコンパイルする、スクリプトから試験者への報告は
**pop しない `Rubevy.ask`**（`tests/pause.rs` の手口。答えを待たないので 1 フレームも損しない）。

6 本の中身と、書いていて分かったこと:

1. **`$x` / `class Foo` / `CONST` が越えない。** 読み手は 3 つを 1 つの数に畳んで返す（1=`$x`、2=`Foo`、4=`CONST`）ので、
   落ちたときに**どれが**漏れたか分かる。定数とクラスは `begin … rescue StandardError … end` で見る。
   そして**同じ読み手を書き手の VM でも走らせて 7.0 が返ることを確かめている**——これが無いと
   「読み手が壊れていて何も見つけられないだけ」と区別がつかない。順序は、書き手を 6 フレーム走らせてから
   読み手を spawn する形にした。2 本の VM の `Tick` の間に順序は無いので、同じフレームに両方立てると
   どちらが先か分からなくなる。
2. **片方の例外が他方を巻き込まない。** `raise "boom"` の側が `ScriptStats::finished` になったことを
   確かめてから、もう片方の鼓動が例外の**後も**増えることを見る。
3. **予算 0 の独立。** `ScriptWorld<A>::budget = 0` にして 40 フレーム回し、A の鼓動が 1 つも増えず
   B の鼓動が増えることを見る。計画書 §3 既定 1「予算は VM ごとの取り分のまま」がそのまま試験になった。
4. **片方のタスクを終わらせても他方は残る。** ここが**唯一書き直した**テスト。
   最初は `remove::<ScriptTask<A>>()` で終わらせたが、A のスクリプトは元気に鼓動を続けて落ちた。
   コードを追って理由が分かった——`Script<A>` はエンティティに残っているので、
   次のフレームの `start_scripts::<A>` が**新しいタスクを作り直す**。これは rubevy の再起動の作法そのもので
   （`tests/replace.rs` がその挙動を試験している）、正しい挙動に間違った質問をしていた。
   `despawn()` に変えた。ついでに、失敗メッセージに 2 つのタスクの `ObjId` を入れてある:
   同じように組み立てた 2 本の VM は同じ添字を配るので、この 2 つはたぶん**同じ数**で、
   名札が無ければ片方を止める呼び出しが隣の VM の赤の他人を殺す、というのが §6.4 の怖さの実物になる。
5. **`ScriptStats` がそれぞれ自分の数を返す。** 忙しいスクリプト（`500.times`）と暇なスクリプト（`sleep` だけ）を
   1 本ずつ別の VM に置き、命令数が 10 倍以上違うことを見る。加えて `location` のファイル名が
   `busy.rb` / `idle.rb` と自分のものになっていることを確かめる——これが「その数字はその VM から来た」の
   いちばん鋭い言い方になる。これも 1 度落ちた: `sabiruby_compiler::Options` の `debug_info` は
   **既定が `false`** なので `location` が `None` だった。テストのコンパイル時に `debug_info: true` にした
   （rubevy 本体の話ではなく、テストが行番号を欲しがっただけ）。
6. **同じエンティティに `Script<A>` と `Script<B>`。** 項目 1 の `ScriptDone<M>` がこのためにある。
   短いスクリプト（すぐ終わる）と長いスクリプト（鼓動し続ける）を同じエンティティに載せ、
   短いほうが終わったあとも長いほうが鼓動し続けることを見る。名札の無い `ScriptDone` のままなら、
   `tick_scripts` の `Without<ScriptDone>` が長いほうのタスクも見なくなるので、ここで止まる。

7 本目は項目 2 の話（上に書いた）。
