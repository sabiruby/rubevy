## 0. 手元で SabiRuby 0.7 を指す方法

SabiRuby 0.7.0 はまだ crates.io に無い。main（`7e03028`）にはあるが、`Cargo.toml` のバージョンは
まだ 0.6.1 のままで、compiler は 0.3.1、serde は 0.2.1。rubevy の `Cargo.toml` に `sabiruby = "0.7"`
と書くと、`[patch.crates-io]` で手元の checkout を指しても、patch の側が 0.6.1 なので要求に合わず
使われない（cargo は「patch が使われなかった」と言って crates.io の 0.7 を探しに行き、無いので止まる）。

SabiRuby 側のバージョンの番号は触らない約束なので、`git archive 7e03028` をスクラッチパッドに展開し、
その**写し**の `Cargo.toml` だけを 0.7.0（compiler 0.4.0、serde 0.3.0）に書き換えて、rubevy と games の
`.cargo/config.toml`（どちらもコミットしない）の patch をそこへ向けた。compiler と serde の番号は
推測で、0.6 のときの対応（「0.3 is the first compiler that names a 0.6.x VM」）を 1 つずつ進めたもの。
公開のときに SabiRuby 側が別の番号を選んだら、rubevy の `Cargo.toml` の 3 行（compiler 2 か所、serde 1 か所）
を合わせる。

`Cargo.lock` は rubevy・games とも**コミットしていない**。patch で書かれた lock は path の crate を
source 無しで記録するので、patch の無い clone では意味を成さない。公開後に作り直す。

## 1. 段階 B（R5）

### 1.1 API の変化

SabiRuby の `CHANGELOG.md` の Unreleased を読み、rubevy が呼ぶものを grep した。
`hash_get` / `hash_delete` / `TaskState` / `catch_tags` / `queues` のうち、rubevy が使っていたのは
`src/reflect.rs:187` の `hash_get` だけだった。`TaskState::queues` の型の変化（`[TaskQueue; 4]`）は
rubevy からは見えない。

`hash_get` は `VmResult<Option<Value>>` になった。ここは Ruby の Hash を Rust の `RubyData::Map` に
読む所で、キーは直前の `hash_keys` が返したものだから「無い」は起きないが、キーの `hash`・`eql?`
が例外を上げることはある。`read_at` はもともと `Result<RubyData, VmError>` を返すので、`?` で上へ
渡すことにした（`unwrap_or(Value::Nil)` で黙って nil にする旧来の形は、0.7 がまさに直した「上がった
ものを捨てる」になる）。

これで全テストが通った（236 件、段階 A の終わりと同じ数）。0.7 の変更で rubevy のテストの期待が
変わったものは無かった。

### 1.2 待てる所が増えたこと

0.7 では `initialize`（`Foo.new`）と `instance_exec` の中でも task が待てる。`docs/host-api.md` の
「A read cannot wait inside `initialize`」の節は、0.6 までの事実を書いていて、0.7 では誤りになる。
確かめるテストを `tests/components.rs` に 2 本足した:

* `a_read_waits_inside_initialize_and_instance_exec` — `initialize` の中の `e[:Hp]` と、
  `instance_exec` のブロックの中の `self[:Hp]` が値を返す。
* `a_read_inside_sort_names_the_boundary` — `sort { }` は今も境界（著者の判断、SabiRuby の
  `wait-anywhere.md`）。その中の読みは `RuntimeError` になり、`rescue` できる。

2 本目の文言は、文書に書く前に実際に出して確かめた。`Array#sort`'s ではなく
`can't wait inside Array#sort!'s call to a block (Task::Queue#pop)` だった（`sort` は内部で
`sort!` を呼ぶ）。host-api.md にはこの実物の文言を書いた。

直した文書:

* `src/prelude.rb` の冒頭のコメント（古い例外の文言）。
* `src/layers/camera.rb` の `attach` のコメント。`attach` は 0.6 の制約から来た形だが、公開した名前
  なので残し、「今は `new` の中でも読めるが、`attach` は残す」と書いた。
* `docs/host-api.md` の「Why a read can wait inside `[]`」の次の節を「Where a read can wait, and where it
  cannot」に書き直し、SabiRuby の `wait-anywhere.md` を引いた。`Rubevy::Proxy` の節にも引用を 1 つ。
  「Adding a second layer」の「`initialize` cannot read the world」の項も直した。

`.rb` のコメントを変えたので `tools/compile_scripts.sh` を回したが、`.mrb` に差分は出なかった
（`mrbc` を `-g` 無しで使っているので、コメントの行ずれは中身に現れない）。

### 1.3 `Rubevy::DroppedQuestion` は 0.7 の `pop` でも効くか

段階 A の `DroppedQuestion` は `Task::Queue#pop` ではなく `__pop_try` の前に立つ（`pop` は Ruby の
ループで `__pop_try` を呼び直す、という mruby-task の作りに頼っている）。0.7 の `ext_task.rs` でも
`__pop_try` はそのまま（`src/builtins/ext_task.rs:1053`）で、`tests/unanswered.rs` の 7 本はそのまま
通った。0.7 で新しく待てるようになった経路でも効くかを見るために、`instance_exec` の中で待っている
問いを捨てる 1 本（`a_dropped_question_raises_inside_instance_exec`）を足し、これも通った。

### 1.4 `Vm::unload` と `ScriptWorld` のプログラムの表

`ScriptWorld::programs` はプログラムの bytes → irep の表で、今までは「SabiRuby に irep を返す方法が
無い」から何も取り除かなかった。0.7 の `Vm::unload(irep)` は、どのフレームもその irep に立って
おらず、Proc も作られていなければ返し、そうでなければ `StillInUse` を返す。まず「使われているかも」
のときに GC を 1 回走らせる（`src/vm.rs:2136-2167`）。

自動で掃除する案（スクリプトが差し替えられたら古いプログラムを返す）を考えて、やめた。理由は 2 つ:

1. 「差し替えられた」を rubevy は知らない。表のキーは bytes で、`AssetId` ではない（同じ bytes の別
   asset は同じプログラム）。差し替えの後に古い bytes を使うスクリプトが残っているかを知るには、
   全 `Script` の asset の bytes を表で引き直す必要がある。
2. 返したプログラムをまた走らせると読み直しになり、1 回ごとに VM に空の irep 1 つ分（208 バイト、
   SabiRuby の CHANGELOG）が残る。短いスクリプトを始めては終える遊び方では、自動の掃除はかえって
   高くつく。

そこで、ゲームが差し替えの時点で呼ぶ `ScriptWorld::unload_programs() -> usize` だけを足した。表の
全部に `unload` を試し、返せたものを表から消す。何が要るかは VM が判断するので安全で、`def` で
メソッドを残したプログラムは返らない（そのメソッドが呼ばれればそのコードが走るから）。
`tests/unload.rs` の 3 本: 差し替えた古いプログラムは返り、走っているものは残る／`def` を残した
プログラムは残る／返したプログラムを再び始めると読み直されて走る。

## 2. 段階 C（R6）

### 2.1 control stage の層（`rubevy::layers::CONTROL`）

元の形（ある組み込み先で 3 回写したもの）は、handler を `define_method` でメソッドにして、`case`
で番号から呼んでいた。0.6 では `instance_exec` の中で待てず、handler の `self` を stage の実体にする
には `instance_exec` が要ったからである。0.7 では待てるので、handler はブロックのまま、
`stage.instance_exec(payload, &block)` で呼ぶ素直な形にした。`tests/control_layer.rs` の
`a_handler_hears_waits_and_keeps_its_state` が、handler の中の `Rubevy.ask(...).pop` が値を返すことを
確かめている（0.6 ならここで task が死ぬ）。

決めたこと（原則に照らして決め、報告に書く）:

* **stage は script ごとに 1 つ**、script の task のインスタンス変数に置く。トップレベルの `self`
  は VM に 1 つの `main` なので、そこのインスタンス変数は全 script で共有になってしまう。
* **payload は 1 引数で渡す**。リストの payload は、ブロックの引数の普通の規則で `|x, y|` に
  展開される。splat するかどうかを層が決める必要が無い。
* **handler が例外を上げたら `Rubevy.log` して聞き続ける**（元の形と同じ。1 通の悪い知らせで残りを
  止めない）。
* **`Rubevy::Control.run` は task を永久に park する**。script の購読は task が終わると手放され、
  handler はそれで `Rubevy::Unsubscribed` を受けて終わるので、handler だけの script は `run` で
  終わる必要がある。止める・差し替える・despawn では handler も終わる（`the_handlers_end_with_the_script`、
  `gc_registered` が 0 まで戻る）。
* 元の形にあった、その組み込み先に固有のもの（イベントごとの引数の表、payload の先頭の件数、
  ゲームの語彙の関数、固定の handler の枠数）は持ち込んでいない。数は 1 つも足していない
  （`on` の `limit:` の既定 nil は「VM の `queue_limit` に従う」の綴り）。

名前は `Rubevy::Control`（計画書の「control stage」から）。

### 2.2 ポインタ（`rubevy::pointer`、feature `pointer`）

「層」の規則（host-api.md「Adding a second layer」）は「Rust を足さない」だが、ワールド座標は
カメラの投影を逆に辿る計算で、どの component にも無い（camera 層の `world_at` がゲームに問うのは
そのため）。だから Ruby の層にはできず、Bevy のプラグインにした。rubevy の既定の依存を変えないため
に cargo の feature `pointer`（`bevy/bevy_camera` と `bevy/mouse`）の後ろに置いた。これを「Camera と
同じ形の任意の層」の Rust 版と読んだ — 使わなければ何も増えない、という点で同じ。

形は元の 3 回の写しと同じ `WorldGrab` / `WorldClick` / `WorldDrop` に、計画書の言う「動いた」
（`WorldMove`）を足した。カメラは型の引数 `PointerPlugin::<C>`（`C` はカメラに付いた marker）で、
元の写しで違っていたのがまさにカメラだった。メッセージには `camera: Entity` を入れた。

試して直したこと: 最初は `WorldMove` を押下の処理より先に書いたので、ドラッグの始まりの 1 回目の
move が `dragging: None` になった（テスト `a_press_that_travels_is_a_drop_and_moves_say_so` が捕まえた）。
順を「grab → ドラッグの判定 → move → drop/click」に並べ直した。読む側にとって自然な順でもある。

テストはレンダラ無しで回すので、`camera_system`（bevy_render）が埋める `Camera::computed` をテストが
書く（800×600 の正射影）。逆行列の誤差で 110.0 が 109.99999 になるので、比べる前に丸めた。

クリックの許容（`DEFAULT_CLICK_SLOP` = 6.0）は測っていない。rubevy_games の `games-shell` と同じ値で、
そちらも出どころを「記録が無い」と書いている。`Pointer::click_slop` で変えられ、`docs/numbers.md`
に「不明」として載せた。

wasm: `cargo build --lib --target wasm32-unknown-unknown --features pointer` が通る。`std::time` も
スレッドも使っていない。

### 2.3 例と文書

`examples/pointer.rs`（`cargo run --example pointer --features pointer`、`[[example]]` に
`required-features`）: ポインタのメッセージをゲームが 1 行ずつ publish し、control 層の script が
`on(:clicked)` の中でゲームに問うて待つ。ヘッドレスで、手の代わりの system がカーソルとボタンを

```
host: the piece is at Vec3(200.0, -80.0, 0.0)
```

## 5. 気づいた点

1. **games の Ruby に 0.6 の回避が残っている。** `garden/ruby/world_prelude.rb:195-200` の
   `each_frame` を `define_method` にしている理由、`garden/ruby/prelude.rb:349` と
   `sabibots/ruby/prelude.rb:164` のコメントが「blocking pop cannot be called from within a C function
   boundary」を前提にしている。0.7 では `instance_exec` で書ける。動いているので直していない。
   games の後続（そのゲーム固有）。
2. **games-shell の `WorldClick` と `rubevy::pointer` が同じ形の 2 本になった。** games-shell の方は
   プレイヤーが動かすカメラと一体。乗り換えるかは games の後続。
3. **SabiRuby の compiler・serde の公開のバージョンが決まっていない。** rubevy はここで 0.4 / 0.3 と
   書いた。SabiRuby の公開の段で違う番号になれば合わせる（計画書の誤りではなく、順番の話）。
4. **`Cargo.lock`（rubevy・games）は公開後に作り直す。** games の `pages.yml` は lock の SabiRuby の
   バージョンから playground のタグを作る（games `docs/plans/author-review.md` C 節）ので、lock を
   上げるときは playground の `SABIRUBY_REF` と合わせて 3 つ一緒に。
5. **本の素材**: 「待てない所」が 0.7 で `initialize` から消えたことで、公開した API（`Camera.attach`）
   が理由を失ったが名前は残る、という形。API の理由が VM の制約から来ていると、VM が変わった後に
   説明だけが古くなる。
