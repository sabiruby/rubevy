# 2026-09-22 crates.io の文面を今の実物に合わせ、0.1.0 を用意する

著者が同じ日に sabiruby の crates.io を見て「各クレートの説明が古いようにみえる」と言い、VM 側は
`sabiruby` `docs/worklog/2026-09-22-readmes.md` でそれを片付けた。rubevy も同じ目で見る。
crates.io のページに出るのは `Cargo.toml` の `description` とその crate の README だけで、docs.rs の
最初のページに出るのは `src/lib.rs` の crate ドキュメントだけである。`docs/` がどれだけ正確でも、
そこは release のときにしか焼き直されない。rubevy 0.0.1 は 2026-09-18 に出たきりで、そのあいだに
R0〜R11 と H1〜H3 が入っている。

ブランチは `release-0.1`、worktree `kishima/rubevy-wt-release`、main の `c9b52a3` から。
**publish もタグも打たない**（本体がやる）。`.rs` の差分は doc コメントだけである
（`git diff main -- '*.rs'` の `+`/`-` 行はすべて `//` で始まる。7 節）。

## 2. 決めたこと — release のたびに古くなる書き方を減らす

sabiruby の `2026-09-22-readmes.md` §2 と同じ判断を rubevy にも当てる。

1. **`## What works` の見出しから版と日付を落とす。** 「今」を言う節に「いつの今か」を書くと、
   直さなかった瞬間に嘘になる。0.0.1 を出したときに誰も `(2026-09-17, v1: tasks)` を直さなかった、
   というのが現にここで起きたことである。どの版に何が入ったかは CHANGELOG が commit ごとに
   持っているので、README の冒頭からそこへリンクし、1 行で書いた。
2. **依存の例の版は caret の幅で書く**（`rubevy = "0.1"`）。patch の release で古くならない。
3. **測った数は出どころのファイル名とセットで書く。** 2.2 µs / 2,667 回は残す価値がある
   （「読みがその行で返る」という主張の唯一の裏づけ）ので、落とさずに
   `docs/worklog/2026-09-17-sync-reads.md` を名指しした。次に測った人が README も直すための
   手がかりになる。
4. **機械の数は書かない。** README に元から無かったので、足さなかっただけ。

## 3. 版

| crate | 今 | → | 理由 |
|---|---|---|---|
| `rubevy` | 0.0.1（crates.io） | **0.1.0** | 下記 |
| `rubevy-build` | 未公開（木の中では 0.0.1） | **0.1.0**（初公開） | 下記 |

**`rubevy` が 0.1.0 である理由。** cargo の semver では `0.0.x` は 1 つ 1 つが互換でないので、
番号の上では `0.0.2` でも `0.1.0` でも同じだけ「壊れうる」。それでも 0.1.0 にするのは、
0.0.1 からの差が「直し」ではなく**面の広がり**だからである: 公開の型と trait が
`FrameStats`・`Held`・`HoldRequests`・`RejectedWrite`・`Program`・`EmbeddedHost`・`CompileFn`・
`layers` と増え、`ScriptWorld` に 15 以上のメソッドとフィールドが増え、`Script` と `ScriptEnded` に
フィールドが増えた。加えて **VM の下限が SabiRuby 0.5.x から 0.6 に動いた**（0.6.0 は
`Vm::current_line` を落とした破壊的な版）。`0.0.x` のままだと「まだ何も決まっていない」と言い続ける
ことになるが、実際には 0.0.1 の名前は 1 つも消えていない。0.1.0 はそれを言う番号である。

**`rubevy-build` が 0.1.0 である理由。** 一度も公開されていないので番号は自由。`rubevy` と同じ数に
するのは、1 つの repo・1 つの CHANGELOG・1 つのタグから一緒に出るからで、「`rubevy` 0.1.0 と
組む `rubevy-build` はどれか」を読む人が考えなくてよくなる。**依存関係ではない** — `rubevy` は
`rubevy-build` を名指ししないし（`[dependencies]`・`[dev-dependencies]`・`[build-dependencies]` の
どこにも無い）、`rubevy-build` は何も名指ししない。慣習であって要件ではない、と
`rubevy-build/Cargo.toml` のコメントに書いた。

**公開の順序は自由**（互いに名指ししないので、片方が index に出るのを待つ必要が無い）。
それでも **`rubevy-build` を先に**出す: `rubevy` の README が
`https://crates.io/crates/rubevy-build` を踏めるリンクとして書いているので、先に出ていれば
`rubevy` のページが描かれた時点でそれが生きている。

**0.0.1 から来る人が直すもの**は CHANGELOG の 0.1.0 の節に "Coming from 0.0.1" として 5 点書いた
（VM の 0.6 への移行、Rust API から消えた名前は無いこと、`Script` / `ScriptEnded` の新しい
フィールドが struct literal を壊さない理由、予約された `ask` の kind が 4 → 7 に増えたこと
（`frame.next`・`resource.get`・`writes.rejected`。0.0.1 の `src/lib.rs:1873` と今の `:3543` を
比べた）、`.crate` に `CHANGELOG.md` が入るようになったこと）。

CHANGELOG の `## Unreleased` は `## 0.1.0 — 2026-09-22` に切り、見出しだけの空の Unreleased は
残さない（sabiruby の CHANGELOG と同じ形）。

内訳（`rubevy`、132 のうち）: `docs/` 49、`tests/` 31、`assets/` 24、`examples/` 11、`src/` 8、

`docs/` の 49 のうち 36 は worklog で、そのうち 1 本はこの文書自身である
（commit 前に数えたときは 131 ファイル・圧縮 626.2 KiB だった）。

**`exclude` は足さない。** 0.0.1 のときの判断（`2026-09-18-crates-io.md`: 87 ファイル・
圧縮 296.2 KiB は上限の 3% 弱）がそのまま延びていて、圧縮 633.8 KiB は crates.io の上限

次に 10 MiB が近づいたら worklog を外すのが最初の手になる（今は遠い）。

`rubevy-build` に `LICENSE` のファイルは入らない（`license = "MIT"` の宣言だけ）。
sabiruby の子 crate 4 つも同じ形である。

## 5. docs.rs

`[package.metadata.docs.rs]` は**無い**ので、docs.rs は既定の feature（= 無し）で建てる。
これでよい: `ruby-source` の裏に公開の名前は 1 つも無く（`#[cfg(feature = "ruby-source")]` は
`src/lib.rs` の 2 か所、どちらも非公開の関数）、`all-features` にすると docs.rs が mruby と
Prism の C を建てることになる。確認は両方で取った（6 節）。

（build・test・dry-run は commit 後の clean な木でもう一度取った数である。）

dry-run は 2 つとも `Verifying` → `Uploading` → `aborting upload due to dry run` まで進み、
エラーは無い。**先に出さないと dry-run が通らないもの**は無い（互いに名指ししないので、
sabiruby 0.6.0 のときのような待ちは起きない）。

**依存は途中で動いた。** 作業中に sabiruby 側が 0.6.1 / 0.3.1 / 0.2.1（説明と README だけの
patch release）を公開したので、`cargo update -p sabiruby -p sabiruby-compiler -p sabiruby-serde` で
lock を上げ直し、**その上で 207 passed** を取った。`Cargo.toml` の要求（`"0.6"`・`"0.3"`・`"0.2"`）は
caret なので 1 文字も変えていない。rubevy 0.1.0 を `cargo add` した人が引くのはこの組み合わせである。

README の絶対リンクは `curl -sI -L` で引いた。GitHub の 5 本が 200、`https://bevy.org/` が 200。
crates.io の 4 本は HTML 側が既定の User-Agent に 403 を返す（bot 避けで 404 ではない）ので
API で確かめた: `rubevy` 0.0.1、`sabiruby` 0.6.1、`sabiruby-compiler` 0.3.1、`sabiruby-serde` 0.2.1、
そして `rubevy-build` は `crate does not exist`（未公開。この release で出る）。

**MSRV は測れていない。** `rust-version = "1.95.0"` はこの機械に入っている toolchain
（stable 1.97.0 と 1.85）では踏めない。根拠は 0.0.1 のときと同じ `cargo metadata` の導出で、
今日引き直して bevy 0.19.1 の 1.95.0 が最大であることを確かめた。この repo に MSRV を踏む
仕掛け（CI も script も）は無い。

## 8. 気づいた点

1. **`docs/plans/publish-plan.md` は 0.0.1 の計画書のまま**で、§5 の表は P1〜P3 が済みで終わって
   いる。今回の release はその計画書の続きではなく（あれは「git 依存を版に替える」という 1 回きりの
   仕事だった）、この worklog がその記録になる。2 回目以降の公開の手順を計画書として残すかどうかは
   著者の判断。**属する先**: 公開の手順。
2. **`rubevy-build` が公開されると、rubevy_games の `[workspace.dependencies]` の
   `rubevy-build = { git = ... }` は crates.io に切り替えられるようになる。** ただし `rubevy` の方は
   git のままにしておく理由（毎日動く、games をその日の rubevy で動かす）が今も生きているので、
   片方だけ crates.io にするのは中途半端になる。games 側の判断材料として書いておく。
   **属する先**: rubevy_games。
3. **README の中の数を誰も見ていない。** 2.2 µs / 2,667 回は repo の中から測り直せるのに、ずれても
   気づく仕掛けが無い（sabiruby の worklog も同じことを 3 つ目の気づきとして書いている）。
   **属する先**: 検証の仕組み。
4. **`Cargo.lock` に rubevy 自身の版が入っている**ので、版を上げるたびに lock も差分に出る。
   これは普通のことだが、「`.rs` は doc だけ」と言うときに lock の行を数えないよう気をつける。
   **属する先**: なし（記録のみ）。
